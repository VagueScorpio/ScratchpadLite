--------------------------------------------------------------------------------
v1.5  -  2026-11-11  -  Phase 5: Markdown, ODT and RTF
--------------------------------------------------------------------------------

What
----

The other three formats, so every format the project promises now opens and
saves.

  * Markdown: MarkdownReader on Markdig, MarkdownWriter by hand. Headings from
    the style sheet's outline levels, bold, italic, strikethrough, nested
    lists with their numbering, pipe tables, links, rules, fenced code for the
    Code style, block quotes for Quote, and images written to a sidecar folder
    beside the document.
  * ODT: OdtWriter, OdtReader, OdtXml, OdtStyleMap and StyleTable, hand-written
    on ZipArchive and System.Xml.Linq. Named styles for the style sheet,
    automatic styles for direct formatting and deduplicated, list definitions
    per marker, tables with merges and shading, pictures under Pictures/, page
    layout, metadata, and the manifest.
  * RTF: RtfFormat on WPF's own converter, with the heading guess, plus a
    header check so a file that is not RTF is refused rather than read as
    rubbish.
  * The save warning learnt the difference between underline and the rest of
    character formatting, because Markdown keeps bold and italic and has no
    underline at all.
  * 542 tests passing (370 in Core, 172 in App), up from 416.
  * The fidelity matrix in USER_GUIDE.md is now measured rather than predicted,
    including three corrections to the blueprint's version.

Measured on this PC, publishing the release build:

    warm startup   656 ms median of runs 2-5 (652, 656, 654, 692)
    budget         1000 ms warm. Cold is not measured here - it needs a
                   reboot - and was 2.0 s budgeted.
    idle memory    144.8 MB working set, 83.1 MB private
    .exe           169.2 MB, up 1.7 MB from v1.4's 167.5 MB (Markdig)
    zip            67.8 MB

Markdig costs nothing at startup: FormatRegistry still creates every handler
through Lazy<T>, and the test that asserts opening a dialog filter loads no
format assembly now names Markdig alongside the Open XML SDK.

Why
---

Three formats, three different reasons for the shape of the code, and the
reasons are worth recording because they are not symmetrical.

ODT is hand-written because nothing free and maintained covers it, and because
the part of ODT this app needs is a zip of XML - which .NET already has.
Markdown is read with Markdig and written by hand: parsing Markdown properly is
genuinely hard and Markdig is the standard answer, while writing it is a matter
of choosing what to escape, and that choice is the whole quality of the output.
RTF is neither, because Windows already has a converter better than anything
worth hand-writing here - at the price of it being someone else's, with limits
this project cannot lift.

The blueprint's fidelity matrix turned out to be wrong in three places, and the
rule is to say so rather than work around it quietly (Section 0: uncertainty).

  * RTF does not keep super- or subscript. The matrix said it did. WPF's RTF
    writer has no \super or \sub keyword at all: it writes the smaller font
    size the editor draws them with, and nothing else, so the text comes back
    small and on the baseline. Fixing this would mean writing RTF by hand,
    which the blueprint ruled out, so it is recorded instead.
  * RTF keeps only one kind of underline. The matrix said "partly", which was
    right to be cautious: all five kinds survive as a plain underline.
  * RTF is better than the matrix expected everywhere else. Tables keep their
    merges, images survive, and links survive - all three were marked "partly"
    and all three are measured here as working.

The save warning's capability flags could not express the Markdown case. One
CharFormat flag covered bold, italic and underline together, so a Markdown save
either claimed it would lose bold, which is false, or claimed it would keep
underline, which is also false. Underline is now its own flag. The cost is one
more flag; the benefit is that the warning tells the truth, and a warning that
cries wolf is a warning people switch off.

Markdown's images go in a folder rather than into the file because Markdown has
nowhere to put them. That makes a save able to leave files behind, so a save
clears out the images this app wrote last time and leaves everything else in
that folder alone - a README or a picture the user put there survives.

How
---

The ODT writer's XML is written with SaveOptions.DisableFormatting, and that is
a correctness choice rather than a size one. Indenting the XML puts newlines
and spaces inside text:p, and in ODT the text inside a paragraph is content: a
reader folds that whitespace into a single space rather than discarding it, so
every indented paragraph gains a leading and a trailing space. "Hello, world."
came back as " Hello, world. " until this was found, which looks exactly like a
reader bug.

A horizontal rule is a paragraph with a bottom border in both ODT and DOCX, and
recognising one has to happen in the block loop rather than in the paragraph
reader - a function that returns a paragraph can only return a paragraph, and
returning an empty one turned every rule into a blank line.

The ODT reader flattens a style's whole parent chain before reading a run, so a
paragraph of Heading 3 arrives already bold. Bold and italic therefore have to
be subtracted against the app's own style sheet exactly as family, size and
colour already were, or the style's own weight becomes direct formatting on
every run and the next save writes it twice. The same applies to the left indent
that Quote carries. This is easy to miss because the two are not nullable in the
IR, unlike the others.

ODT list definitions are now one per marker rather than one for bullets and one
for numbers, because the numbering format lives in the definition and not on the
list that uses it. A list that does not start at one says so with
text:start-value on its first item.

ODT column widths are automatic styles. There is no width attribute on
table:table-column, so a table whose columns have no styles is a table of equal
columns however the IR describes it - the widths were simply never written
before.

The cell shading styles the ODT writer declares were held in a static
dictionary, drained when content.xml was built. Two documents saving at once
would have mixed their styles. They are per-document now, alongside the column
and list styles.

Markdown escaping is split in two. EscapeInline handles what is syntax anywhere
in a line; EscapeBlockStarts handles what is syntax only at the start of one,
which cannot be decided while a run is being escaped because the run's position
in the line is not yet known. So "# not a heading" goes out as "\# not a
heading" and "1. not a list" as "1\. not a list", escaping the delimiter rather
than the digits. An underscore inside a word is left alone - CommonMark says it
is not emphasis, and a file full of \_ cannot be read as text, which is the only
reason to use Markdown at all.

A Markdown file nested deeper than Markdig's own limit is refused with a
readable message. Markdig throws ArgumentException rather than overflowing the
stack, which is the right thing to do, but an opened file is untrusted
(Section 7.5) and has to come out as a bad file rather than as a bad argument -
otherwise the user is told only that it "could not be opened".

Three bugs in FlowWalker came out of the RTF tests, all the same shape: the
walker assumed the tree its own builder produces, and WPF's RTF reader nests
differently.

  * A hyperlink's content is not always a flat list of runs. WPF's reader puts
    a Span inside the Hyperlink, and the walker looked only at direct Run
    children, so every link in an opened .rtf lost its text entirely - not
    just its target.
  * TextDecorations and Background do not inherit in WPF's property system
    although they render as though they do: a Span marked underlined draws
    every run inside it underlined while each of those runs reports an empty
    TextDecorations of its own. Both are now collected by walking up the inline
    chain, which stops at a hyperlink, whose underline belongs to the link
    style rather than to the text.
  * An image that arrives without original bytes is encoded as PNG from its
    bitmap instead of being dropped. The pixels are there and PNG is lossless,
    so a re-encode is a better answer than a missing picture. This is what
    makes pictures in an opened .rtf survive, and it will do the same for
    pasted ones in Phase 6.

None of the three could have been found by testing the bridge against itself,
which is the general lesson: a round trip through your own code proves only
that it is self-consistent.

v1.4  -  2026-11-09  -  Phase 4: the IR, the bridge, TXT and DOCX
--------------------------------------------------------------------------------

What
----

Files open and save. The architecture the whole of Section 4 is built around
is now real rather than described.

  * IrNormalizer and IrComparer: canonical form and content comparison for
    documents, which is what makes the round-trip test possible, plus a
    readable dump of a document for when it fails.
  * FlowBuilder: IR to FlowDocument. Paragraphs, the eleven styles, alignment,
    indents, spacing, line spacing, page breaks, lists nested into WPF List
    elements, tables with spans and shading, horizontal rules, images with
    their original bytes kept, hyperlinks, and the five underline kinds.
  * FlowWalker: FlowDocument back to IR, reading each run's effective values
    and recording only what differs from its paragraph style.
  * SpProps gains the markers the bridge needs: the horizontal-rule style
    name, a hyperlink's original target, and an image's bytes and MIME type.
  * IFormatHandler and FormatRegistry: the format table, the Open and Save As
    dialog filters, and the capability sets the save warning reads.
  * IrFeatures: which features a document actually uses, so the save warning
    names only what this file would lose.
  * TxtFormat: encoding detection (BOM, then strict UTF-8, then
    Windows-1252), line-ending detection and preservation, lists with markers,
    tables as tab-separated rows.
  * DocxWriter: the body, a full style sheet, numbering definitions, tables
    with row and column spans, images as image parts, page setup and the core
    properties.
  * DocxReader: style resolution through basedOn and the document defaults,
    runs, paragraph styles matched by name, lists through the numbering
    definitions, tables, images, hyperlinks, page setup and metadata.
  * FileOps: the safe-save path - temporary file in the same folder, flushed
    to disk, then File.Replace with an optional .bak - and a plain sentence for
    each of read-only, locked, disk-full, folder-gone and path-too-long.
  * DocumentSession and DocumentIo: one open document, and the open/save flow
    from Section 4.4 - read and write off the UI thread, build and walk on it.
  * The File menu works: New, Open, Open Recent, Save, Save As. Plus the
    window title with a dirty marker, a warnings bar for what a file could not
    carry, the lossy-format dialog, the changed-on-disk check, the
    unsaved-changes prompt on close, and files named on the command line.
  * RecentFiles, written on every open and save so it survives a crash.
  * 415 tests passing (270 in Core, 145 in App).

Measured on this PC:

    warm startup      683 ms median of runs 2-5 (Phase 3: 705 ms)
    with a .docx on   660 ms, and the file was open and rendered before the
    the command line  measurement ended
    idle memory       146.5 MB working set, 83.4 MB private
    with a document    163.2 MB working set
    .exe              167.5 MB, up from 142.8 MB
    log               no warnings and no errors

Why
---

The IR earns its place in this phase, so it is worth restating what it buys. A
FlowDocument belongs to the thread that owns the window, which means a format
handler that worked on one directly would have to parse a 200-page .docx on the
UI thread, and the window would be frozen while it did. Because every handler
reads and writes plain records instead, the slow part runs on a background
thread and only the final tree build touches the UI. The same split is why
every format handler is tested without opening a window at all.

The other half of the argument is the number of conversions. Five formats and
one editor is five converters through an IR, and would be ten without one -
and each of those ten would have its own ideas about what a heading is.

The rule both sides of the bridge follow, and the reason the round-trip test
can be strict: only direct formatting is written. A run whose font and size
match its paragraph style carries nothing at all. Without that rule a heading
saved to .docx would come out as directly formatted 20-point bold text that
Word no longer knows is a heading - no navigation pane entry, no table of
contents, and no way to restyle it.

How
---

The round-trip test is the one Section 6.4 calls the most important in the
project, and it is 56 cases: every character format, every underline kind,
every paragraph style, every list format, nesting, tables with spans and
shading, images, links, line breaks, page breaks, metadata and page setup,
then one document using all of it at once. It compares
Normalize(Walk(Build(d))) with Normalize(d), and the normaliser is allowed to
discard only what a reader could not perceive: adjacent runs with identical
formatting merged, empty runs dropped, colours upper-cased, sizes rounded to
three decimal places because they make the trip through DIPs and 10.5 pt comes
back as 10.499999999999998. Every other difference is a bug, and it found
three.

  * A list that changed kind silently lost its numbers. The builder gathered
    each run of consecutive list paragraphs into one WPF List element, so a
    numbered list immediately after a bulleted one was folded into the bullet
    list and came back out as bullets. It now starts a new list whenever the
    marker changes, and returns several roots rather than one.

  * A style with no font of its own resolved to whatever WPF felt like. Most
    styles in the sheet leave Family null, meaning "whatever Normal uses", and
    the builder took that literally and set nothing - so the paragraph
    inherited WPF's own default font and the walker read that back as the
    run's font. A heading came out of a round trip in a font nobody had
    chosen. Both sides now resolve it through StyleSheet.FamilyFor.

  * A hyperlink's blue was being recorded as a colour someone chose. A run
    inside a Hyperlink reports the link style's blue as its effective
    foreground, and the walker wrote it into the IR as direct formatting.

And the .docx writer had three of its own, all of which produced files that
looked fine until something checked them properly.

  * WordprocessingML is a sequence, not a set. w:rPr must hold its children in
    one specific order, and a file with w:sz before w:b is invalid even though
    every element in it is legal - Word refuses it as unreadable content. The
    same applies to w:pPr, where spacing comes before indentation and both
    before justification, and to w:style, where pPr comes before rPr. The
    writer now puts them in order from one list per element rather than in the
    order the code happens to produce them. The SDK's own OpenXmlValidator is
    what caught it, which is exactly why Section 7.2 asks for it.

  * Row spans were written with no continuation cells. Word spans rows by
    marking the top cell "restart" and putting a "continue" cell in each row
    below it. The IR leaves those out - a spanned cell simply occupies the
    rows beneath - so the writer has to put them back, and without that a
    two-row span came out of a file as a one-row cell.

  * The Code style's own shading came back as a highlight. A style with
    shading gives every run in it that shading as an effective value, and the
    reader was recording it as something the user had applied.

A note on links: Uri canonicalises, so "https://example.com" comes back as
"https://example.com/". That is the same address by the URI specification
rather than a loss, so IrNormalizer puts absolute URLs through Uri and
compares them that way. Anything that is not an absolute URL - a relative
path, a bookmark, or something a file simply claimed - is left exactly as it
was.

Dependencies
------------

DocumentFormat.OpenXml 3.5.1, MIT. Section 2.1 says the size and startup cost
of a package is measured and recorded when it goes in, so: the .exe grew from
142.8 MB to 167.5 MB, which is about 25 MB, and warm startup did not move -
705 ms before, 683 ms after. The reason startup is unaffected is that
FormatRegistry creates every handler through Lazy<T> and its format table
mentions no format type outside a lambda body, so nothing loads the SDK until
a .docx is actually opened or saved. A test asserts that: it builds the Open
dialog filter and then checks that neither SDK assembly has been loaded.

Twenty-five megabytes is a real cost on a 167 MB .exe and it is worth saying
plainly. The alternative is writing a .docx reader and writer by hand, which
is thousands of lines of someone else's XML schema, or not supporting Word
documents - and the latter is not on the table.

Two smaller notes:

  * System.IO.Packaging is pinned at 10.0.14 explicitly. The version the Open
    XML SDK asks for transitively has a known high-severity advisory
    (GHSA-f32c-w444-8ppv), and because this project builds warnings as errors
    the restore refused it rather than letting it through quietly - which is
    the warnings-as-errors setting earning its place.
  * System.Text.Encoding.CodePages was not needed after all. The blueprint
    expected a package for Windows-1252; .NET 10 has it built in, and adding
    the reference was refused with NU1510, "this package is automatically
    available".

Not built in this phase
-----------------------

  * Markdown, ODT and RTF are Phase 5, as planned. The Open dialog does not
    offer them, so nothing pretends to work.
  * Only the first file named on the command line is opened. Tabs are Phase 7;
    until then a second file would have nowhere to go, and the status bar says
    so rather than dropping it silently.
  * An image pasted into the editor has no original bytes to keep, so the
    walker skips it. Phase 6 encodes those as PNG when pasting is wired up.
  * The missing-font bar now has a caller - opening a document - which it did
    not in Phase 2.

Watch
-----

Idle working set is 146.5 MB against the 150 MB in Section 2.1, and 163.2 MB
with a document open. Private bytes are 83.4 MB. The question of which figure
Section 2.1 means has been open since the Phase 1 report; on the working-set
reading there is now effectively no headroom left, and Phase 6's tables and
images will not make that better.

v1.3  -  2026-11-09  -  Phase 3: the rest of the font formats
--------------------------------------------------------------------------------

What
----

Everything else that can hold an outline font now works in the fonts/ folder.

  * Type1Parser: the PFB and PFA wrappers, the eexec layer and the charstring
    layer, the font and Private dictionaries, the encoding, the subroutines and
    the charstrings. Multiple Master and CID-keyed fonts are named and refused
    rather than half-converted.
  * CharStringConverter: a Type 1 charstring interpreted into an outline -
    subroutines inlined, flex curves assembled, accented characters composed
    from their two component glyphs, division and hint replacement handled,
    hints dropped.
  * Type2Writer: that outline written back out as a Type 2 charstring.
  * CffWriter: the CFF table - header, INDEXes, Top DICT, charset, Private
    DICT.
  * SfntTables: head, hhea, maxp, hmtx, post, OS/2, name and cmap synthesised
    for a font that carries none of them, with format 4, format 12 above
    U+FFFF, and a (3,0) symbol subtable for a font whose glyph names mean
    nothing outside it.
  * GlyphList: the Adobe Glyph List, 4281 names, embedded - plus the uniXXXX
    and uXXXX forms, variant suffixes such as a.sc, and underscore ligature
    names.
  * AdobeEncodings: StandardEncoding, which seac needs and which a font that
    declines to list its own encoding relies on.
  * AfmPfmReader: the binary .pfm and the text .afm, for the Windows family
    name, the style bits, the weight class and the published widths.
  * EotDecoder: the EOT header walked, the XOR mask undone, the font
    underneath rebuilt. MicroType Express files are refused by name.
  * Type42Extractor: the hex strings of a /sfnts array reassembled.
  * MacFontExtractor: .dfont, AppleDouble ._* files and data-fork suitcases -
    the resource map walked, sfnt resources extracted, and POST resources
    joined back into PFB data so Mac Type 1 fonts go through the Type 1 path.
  * All of it wired into the folder pipeline, with the Font Report naming the
    format each file was converted from.
  * 276 tests passing (197 in Core, 79 in App).

Measured on this PC, with a sixteen-file font folder covering every format:

    warm startup      705 ms median of runs 2-5. Phase 2 was 669 ms and Phase 1
                      699 ms, so still nothing on the startup path.
    index load        10 families from 17 entries in 4 ms
    first run         13 files prepared in well under a second, in the
                      background
    idle memory       144.4 MB working set, 81.0 MB private
    .exe              142.8 MB (up 0.6 MB, which is the Adobe Glyph List)
    log               no warnings and no errors

Why
---

A Type 1 font has outlines, widths and glyph names, and nothing else. No
character map, no metrics tables, no name table in any form an OpenType
consumer can read. So "converting" one is really two jobs: translate the
outlines, and invent - correctly - everything else a modern font is expected to
carry. That is why this phase is mostly SfntTables and the Adobe Glyph List
rather than charstring arithmetic.

The glyph list is the part worth explaining. A Type 1 font says a glyph is
called "eacute"; it does not say that means U+00E9. The only way to build a
cmap is to look every name up in Adobe's published list, which is why 78 KB of
it is embedded. For a symbol or dingbat font the names are the designer's own
invention - "a12", "H18533" - and mean nothing to anybody, so those get a
symbol cmap built from the font's own encoding at U+F020 upwards instead. The
choice between the two is made by counting how many of a font's names the list
recognises, because doing it name by name would give a font with a few
recognisable names a half-working cmap, which is worse than either answer.

Charstrings are converted in two passes - interpret to an outline, then emit -
rather than translated operator by operator. Type 1 has features Type 2 has no
equivalent of: subroutines that return values, flex curves written as seven
separate moves, accented characters that reference two other glyphs by
StandardEncoding code, and division. Going through a plain outline makes all of
that local to the interpreter.

How
---

Three bugs found by testing, each of which had produced something that looked
entirely valid.

  * A C# precedence trap in the CFF writer. "total + 1 switch { ... }" parses
    as "total + (1 switch { ... })", not "(total + 1) switch { ... }", so the
    INDEX offset size came out as the size of the whole INDEX rather than 1 to
    4 - and every offset was then written in that many bytes. A 105 KB
    CharStrings INDEX became 95 MB, and a 140 KB font converted to a 95 MB one.
    Nothing else noticed: the font was still structurally valid, FontInspector
    read it, and the only clue was the size. Both branches now have
    parentheses and a comment.

  * The CFF offsets were written into a copy. The Top DICT holds byte offsets
    to the charset, the CharStrings INDEX and the Private DICT, and they can
    only be filled in once those parts have been measured - so the DICT is
    built with five-byte placeholders and patched afterwards. But the patching
    happened after the DICT had already been wrapped in its INDEX, and
    wrapping copies the bytes. Every offset in the font that shipped was
    therefore zero. DirectWrite's entire diagnosis of this was "Invalid file
    format".

  * The PFA reader swallowed the trailer. A Type 1 program ends with 512 zeros
    and the word "cleartomark", and those zeros are perfectly good hex digits.
    A decoder that reads hex until something is not hex therefore absorbs 256
    bytes of padding into the encrypted data, discovers the problem only at
    "cleartomark", and then - in the first version here - fell back to treating
    the whole section as binary, leaving the private dictionary unreadable and
    the font apparently corrupt. Hex or binary is now decided from the first
    four non-blank characters and then stuck to, and the hex stops at the
    first character that is not one.

One design decision rather than a bug: Type 42's pad-byte rule cannot be
resolved by a reader. The specification says each string in the /sfnts array is
padded to an even length, but nothing records whether a pad byte was added, so
a 2048-byte string could be 2048 bytes of font or 2047 and a pad. Guessing
wrong either way corrupts every table after the first split. Both readings are
tried and the one that produces a font with a readable family name wins -
which needs no guess, and is also why that check has to be the family name
rather than merely "it parsed": the wrong reading parses happily, because the
header and the table directory are in the first chunk and intact either way.

Two notes about testing fonts through WPF, because a day went into them:

  * WPF's font cache is keyed by directory. Load several fonts from one folder
    and the first works while every one after it throws - sometimes
    FileFormatException, sometimes a NullReferenceException from inside
    MS.Internal.FontCache - whether or not the fonts are valid. Each font in
    the tests now gets a directory of its own.
  * Metrics must be read through "new GlyphTypeface(uri)". Going via
    Fonts.GetFontFamilies, then a Typeface, then FormattedText throws
    FileFormatException for a font loaded out of a file - and does it for an
    untouched arial.ttf as readily as for a converted one, which is what
    finally separated the harness problem from the real conversion bugs above.

Smaller things:

  * The PFM field offsets were four bytes out: dfFace is at 105, and 101 is
    dfDevice, which for a printer font reads "PostScript". Every converted
    font was briefly called "PostScript Regular".
  * A .pfm or .afm sitting beside its font used to be reported as "the outline
    file (.pfb) is missing", which sends the user looking for something they
    already have. It now says what it is metrics for, and only reports a
    missing outline when the outline really is missing.
  * SfntTables is the other half of what Section 5.1 called SfntBuilder - the
    table synthesis, as opposed to the container assembly in Sfnt.Build. The
    name was left behind in Phase 2 for the reason recorded there.

Not built in this phase
-----------------------

  * Hints are dropped, which Section 6.6.4 allows. A converted font can look
    slightly soft on screen at small sizes; printing is unaffected.
  * MicroType Express compressed EOT files. That is a Monotype compression
    format with no free implementation, and Section 13 already lists it as
    unsupported. They are refused by name.
  * Multiple Master and CID-keyed Type 1 fonts, as Section 6.6.3 says.

Tested against what
-------------------

Worth being plain about, because the fixtures are what the confidence rests on.

  * Type 1: four URW text fonts with their AFMs (Nimbus Roman Regular and
    Bold, Nimbus Sans, Nimbus Mono PS), Adobe's Symbol with its PFM, and
    Adobe Sans MM and Adobe Serif MM as negative fixtures. All six are real
    files produced by real tools. WPF reads 855 glyphs, 854 cmap entries and
    855 non-zero advance widths out of each converted text font, and draws
    outlines from them.
  * EOT: four real files, three from Adobe Acrobat and one from Typora. All
    four recover and load.
  * Type 42 and the Mac containers: no .t42, .dfont, .suit or ._* file exists
    anywhere on this machine, so those tests build their fixtures from a
    Windows font. That proves the readers understand the formats as written
    here, which is weaker than testing against something another tool
    produced. If you have real ones, dropping them into tests/Fixtures/Fonts
    is all it takes - the tests pick up whatever is there.
  * A PFA was also built from a PFB to exercise that wrapper, and it is what
    found the cleartomark bug above.

v1.2  -  2026-11-08  -  Phase 2: fonts
--------------------------------------------------------------------------------

What
----

The fonts/ folder works. Drop fonts next to the .exe and they turn up in the
picker, prepared in the background after the window is already on screen.

  * Sfnt: reading and writing the OpenType container - header, table
    directory, checksums, collections - with every offset bounds-checked.
  * FontInspector: family and face names, version, copyright, licence text and
    URL, fsType, glyph count, whether the font has Latin letters, and whether
    it is a variable font. Reads raw bytes and needs no WPF.
  * WoffDecoder: WOFF 1.0, each table inflated with the built-in ZLibStream.
  * Woff2Decoder: WOFF 2.0 - the Brotli stream, both variable-length integer
    encodings, and the transformed glyf, loca and hmtx tables rebuilt.
  * FontTypeDetector: what a file actually is, from its first 64 bytes, with
    the extension only consulted for formats that have no signature.
  * FontScanner: one recursive listing of names, sizes and times.
  * ZipFontSource: fonts read straight out of a .zip, one entry at a time,
    never unpacked into fonts/.
  * FontCache: prepared fonts at data/font_cache, named by content hash.
  * FontIndex: data/font_cache/index.json, one card per source file,
    source-generated JSON with a version field.

Why
---

The index is the whole performance story, so it is worth being plain about what
it buys. A launch with an unchanged font folder reads one JSON file and
registers every family from the names stored in it - no font file is opened,
nothing is hashed, nothing is copied. WPF reads a font only when text is
actually drawn in it. That is why 687 fonts cost 9 ms and not nine seconds, and
why the startup figure above is the same whether the folder holds nine fonts or
seven hundred.

Fonts are copied into a cache rather than loaded from fonts/ because WPF keeps
a font file open for as long as the family is registered. Loading in place
would mean the user cannot delete, rename or replace their own fonts while the
editor is open. Naming the copy by content hash means an updated font gets a
new cache file instead of fighting over the old one, and two files holding the
same font share one copy.

A font bundle downloaded from the web almost always holds the .otf, the .woff
and the .woff2 of every font. Without duplicate detection the picker shows one
name three times and the cache holds three copies of the same outlines, so the
.ttf or .otf is kept and the rest are marked "Duplicate of ...".

A font in fonts/ wins over an installed font of the same name. Someone who put
a font there did it on purpose.

How
---

Three things were found by measurement rather than by reading, and they are the
substance of this phase.

  * The WOFF2 bounding-box bitmap is padded to four bytes, not one. One bit
    per glyph, and the obvious ceil(n/8) is right for the number of bits and
    wrong for the size of the field: with 2901 glyphs it gives 363 bytes where
    the answer is 364. Every bounding box after it is then read one byte out of
    step, so every composite glyph in the font came out as two halves of its
    neighbours - accented capitals with their left edge past their right edge.
    What makes this worth recording is which fonts can catch it. A font whose
    glyphs are all simple outlines stores no bounding boxes at all, reads
    nothing after the bitmap, and decodes perfectly either way: four of the
    seven test fonts were in that group and said nothing. Only a font with
    composite glyphs - an accented Latin font, or CJK - fails. Testing against
    one real font would not have been enough.

  * The 255UInt16 escape codes are the way round that looks wrong. Code 255
    adds 253 and code 254 adds twice that. Swapping them was tried, on the
    theory that the pair had been transcribed backwards, and three more test
    fonts failed immediately - so the original was right, and the comment in
    Woff2Reader now says so and says how it is known. The codes only appear on
    glyphs with 253 points or more, which is why most fonts decode either way
    and a CJK font and an icon font are what settle it.

  * Preparing a large font folder used 772 MB and kept 732 MB of it. The
    budget in Section 2.1 is 150 MB, so this was the real work of the phase,
    and it took three separate fixes. First, FontInspector was reading fonts
    through the table-copying reader: for a reader that wants four of a font's
    twenty tables, that is the whole font copied to look at a fifth of it, so
    inspecting 396 MB of fonts allocated another 396 MB. A zero-copy directory
    reader - tags and offsets, with the tables read in place - took the peak
    from 772 MB to 353 MB. Second, the file reads were going through
    ArrayPool<byte>.Shared, which keeps its buffers on purpose and cannot hold
    anything over 1 MB: 70 MB of live buffers were still held after the pass.
    A pool scoped to the pass, dropped when it ends, took the live managed heap
    from 70 MB to 6 MB. Third, that pool's buckets are powers of two, so
    allowing it up to the 50 MB file cap let it hold one buffer of 1, 2, 4, 8,
    16, 32 and 64 MB at once - about 127 MB for reading one file at a time.
    Capping pooling at 4 MB and giving the handful of larger fonts a plain
    array each brought the peak to 247 MB and the settled figure to 162 MB.
    What is left is 6 MB of live managed memory and the runtime's own committed
    space, so there is nothing still being held.

One bug worth its own note, because the test suite could not have caught it:

  * A UI callback with no inline fallback. FontRegistry marshals its progress
    and change notifications onto the UI thread, and when there was no
    Application it ran them inline instead. That is exactly the state during
    --measure-startup, which shuts down at the first frame: the callback then
    touched the status bar from the preparation thread, threw "the calling
    thread cannot access this object", and took the whole folder check down
    with it - so the index was never saved and every measurement run prepared
    the entire font folder again from scratch. It was visible only as four
    ERROR lines in the log and a startup figure that would not settle. There
    is no sensible inline fallback for a UI update: if there is no UI, there is
    nothing to tell. --measure-startup now also skips font preparation
    outright, because a measurement run doing work a real launch would not is
    not a measurement.

Two deliberate deviations from the blueprint:

  * Section 6.6.2 step 6 says to read the family names by loading the font once
    with WPF's Fonts.GetFontFamilies. FontInspector reads them out of the name
    table instead. Two reasons: WPF keeps a font file open once it has read it,
    which is the thing the cache copy exists to avoid, and reading names
    through WPF would put a WPF dependency in Core, where the compiler is set
    up to refuse one. The App tests load every decoded font through WPF and
    check its families and glyph count, so the guarantee that mattered - that
    DirectWrite can actually read what was produced - is still tested, just
    not during preparation.

  * SfntBuilder was listed in Section 5.1 under Fonts/Type1/, described as
    "shared by every decoder and converter". The WOFF decoders need it in
    Phase 2 and Type 1 is Phase 3, so the shared container code is
    Fonts/Sfnt.cs and the stub under Type1/ is gone rather than left throwing.
    A shared helper filed under one caller's folder is misleading about who
    uses it. Phase 3 still needs the other half of what that name covered -
    synthesising head, hhea, maxp, hmtx, post, OS/2, name and cmap for a
    converted Type 1 font - and that belongs with the Type 1 code.

Not built in this phase
-----------------------

  * WOFF2 font collections. Section 6.6.5 asks for them. A collection needs a
    second directory, shared glyf and loca tables across fonts, and a third
    index layer, and web fonts are effectively never collections - no .woff2
    collection was found to test against. A collection is refused with a
    message naming the .ttc or the individual .otf files instead, which is
    checked by a test. Say the word if it should be built anyway.

  * Adobe Type 1 (.pfb, .pfa), Mac containers (.dfont, ._*), EOT and Type 42.
    These are Phase 3 as planned. They are detected and named now, so the Font
    Report says each one cannot be used yet rather than ignoring the file.

  * The missing-font bar is built and tested but has no caller: it lists the
    fonts a document asked for, and nothing can open a document until Phase 4.

Watch
-----

Idle memory is 144.9 MB working set against the 150 MB in Section 2.1, which is
where Phase 1 left it - the font system added about 1 MB for nine fonts and
about 5 MB for 687. Private bytes are 81.8 MB.

The run that prepares a very large font folder is the exception: over 396 MB of

state and it holds 6 MB of live managed memory, so it is the runtime's
committed space rather than anything retained, but on the working-set reading
it is over the line. The question of which figure Section 2.1 means is still
open from the Phase 1 report.

Why
---

Everything after this phase edits a document, so the document had to come
first, and the two decisions worth recording are about what formatting means
rather than how it is stored.

Clear Formatting returns a paragraph to its style rather than to nothing. A
heading with Clear Formatting applied should still be a heading; it is the
by-hand changes on top that go. That is what Word does and what Section 6.5
describes, and it is why ClearAllProperties alone is not the whole command -
the paragraph's style is re-applied afterwards.

Change Case rewrites the letters instead of setting a format. WPF has no
all-caps character format, so there is nothing to save to a .docx; changing the
letters themselves means the result survives every format in Section 7, which
is the point.

The paste filter downgrades XAML to RTF to plain text. WPF offers pasted
content as XAML, and XAML is not markup here - it is a serialized object graph
that the control would instantiate. Pasting from a web page should not be able
to construct objects, so that flavour is dropped before it is read.

Themes arrived two phases early. Section 6.16 puts them in Phase 8, but the
toolbar button styles need themed brushes to render at all, and a toolbar
styled against hard-coded colors now would have to be unpicked later. The
dictionaries, ThemeManager and the dark title bar are therefore in, which is a
deviation from the phase plan in the direction of less rework.

How
---

Five things about WPF turned out differently from the blueprint or from the
obvious implementation. Each one is recorded where it bites, in the code as
well as here.

  * TextRange cannot carry the attached properties. Sections 6.4 and 6.8 say
    to store the underline kind, the super/subscript alignment and the base
    font size through the selection, but TextRange.ApplyPropertyValue and
    GetPropertyValue accept only WPF's own text-formatting properties and throw
    ArgumentException - "'Underline' property is not valid for text
    formatting" - for anything else. This is not a detail; it is the mechanism
    two sections of the blueprint are built on, and it broke 14 tests.
    What replaces it: SpProps.ApplyToSelection and ReadFromSelection walk the
    inline elements the selection covers and set or read the value on each one,
    and all five properties are registered with
    FrameworkPropertyMetadataOptions.Inherits so a value set on a span is still
    readable from the runs inside it. Call order matters and is commented at
    every call site - the real WPF property goes on first, because applying it
    is what makes WPF split runs at the selection edges, and the attached
    property then lands on the runs that now exist.

  * Commands have to be public, and the test suite had to be able to say so.
    The menus reach the commands with {x:Static}, which XAML resolves at parse
    time by public reflection. The commands were internal. That compiled
    without a warning, every unit test passed, and the app threw
    ArgumentException the instant MainWindow's XAML was parsed - dead before
    its first frame, on every launch. The real fault was in the tests: each
    one checked a class in isolation and nothing ever loaded the window.
    MainWindowTests now builds the real MainWindow, shows it, lays it out and
    reads the commands back off the menu items, and AppHost gives those tests
    one STA thread with a real Application so the toolbars find their
    StaticResource styles. The rule from here: anything the app parses or
    renders at startup is loaded by a test, not just the classes behind it.

  * Application.ThemeMode is still experimental in .NET 10. It exists, but
    using it raises WPF0001, and this project builds with warnings as errors,
    so taking it would mean suppressing a diagnostic that says the API may
    change. The hand-written Light and Dark dictionaries stay, and a test
    asserts the two have identical key sets - a key present in one and missing
    from the other shows up as an unpainted control, which is easy to ship and
    hard to spot.
    Writing that test found a second thing: ThemeManager loaded its dictionary
    from the relative URI "UI/Themes/Light.xaml", and a relative pack URI
    resolves against the entry assembly. That is this one when the .exe starts
    the process, and the test runner otherwise, so the theme failed to load
    with "Cannot locate resource" under test. It now builds the full
    pack://application URI with this assembly named, taking the name from the
    assembly rather than a string, and both the app and the tests go through
    the same method.

  * Undo needs a hosted control. CanUndo is false for every edit on a
    RichTextBox that is not in a visual tree, a plain text change included, so
    the first version of the undo tests was asserting something that could not
    be true. They now show a window with ShowActivated false, which gives a
    live undo stack, and the test that earns BeginChange/EndChange its place is
    the double underline: it writes two text decorations and an attached
    property, and one Ctrl+Z has to take back all of it.

  * The two drawn underlines and the paper shadow are hand-made. WPF offers
    one underline, so double is two pens at different offsets, dotted and
    dashed are dash patterns, and wavy is a tiled DrawingBrush of bezier
    curves; all of them are frozen, since they never change. The paper shadow
    is two offset borders rather than a DropShadowEffect, because an Effect
    allocates a render target the size of the whole document.

Two smaller notes:

  * Superscript applied over subscript would have shrunk the text twice, to
    4.2pt from 10pt, which is why the base size is kept in an attached property
    and the size is computed from it rather than from the current size. There
    is a test named for that case.
  * The selection readout runs at DispatcherPriority.Background behind a 50 ms
    throttle, and the word count behind a 300 ms timer. Both run on every
    keystroke otherwise, and typing is the one thing in this app that must
    never feel slow.

Not built in this phase
-----------------------

  * Show Formatting Marks. WPF cannot draw paragraph marks and space dots
    inside a RichTextBox without a custom adorner. The menu item is present and
    disabled with a tooltip saying so, rather than half-built or quietly
    missing.
  * The font picker lists the fonts Windows has. The fonts/ folder, the
    converted formats and the Font Report are Phase 2 and 3, as planned.

Watch
-----

Idle working set went from 124.1 MB in Phase 0 to 143.6 MB here, against the
150 MB in Section 2.1. Private bytes are 81.6 MB and comfortable; the growth is
in the mapped pages that come with parsing this much more XAML. Phase 2 adds
the font index, so on the working-set reading the budget is close to spent. The
question of which figure Section 2.1 means is raised in the Phase 1 report
rather than decided here.

What

The project outline, and the parts of it that have to work before anything can
be built on top:

    written atomically, falling back to defaults when the file is missing or
    damaged.
  * Log: a rolling daily file in data/logs, 1 MB per file, 7 days kept, opened
    lazily on its first write so startup pays nothing for it.
  * CommandLineOptions: file paths, --measure-startup, --debug, --fonts.
  * App: the startup sequence, with crash handlers for the UI thread, the
    app domain and unobserved tasks.
  * StartupTimer and --measure-startup.
  * MainWindow: the window with the full menu structure from Section 8.1 and a
    status bar. Items whose phase has not arrived are disabled rather than
    missing, so later phases wire up menus that already exist.
  * Theme dictionaries (Shared, Light, Dark) and ThemeManager.
  * The whole source tree from Section 5.1, each file carrying the blueprint
    section it implements and the phase it is due.
  * build/build.ps1: tests, publish, font bundle, documents, the startup
    measurement, the zip, and the sizes and hash.
  * fonts/README.txt, and the font folder left otherwise untouched.
  * 13 tests passing (command line, settings, paths, startup timer).

Why
---

Phase 0 exists to make the later phases cheap. Three things in particular had
to be settled before any feature work:

  * Where files live. A portable app that guesses wrong about its data folder
    is broken on a USB stick and broken in Program Files, and that is hard to
    retrofit, so AppPaths and the read-only fallback come first.
  * The startup budget. Section 2.1 is the top-priority rule in the blueprint,
    and a budget nobody can measure is not a budget. The timer, the hidden
    measurement flag and the median in build.ps1 exist so every later phase can
    be checked against the number rather than against an impression.
  * The shape of the tree. Every file in Section 5.1 is present as a documented
    stub, so a phase starts by filling in a file that already knows what it is
    for, and nothing has to be reorganised halfway through.

The full menu structure is in the window for the same reason: the shortcut table
in Section 8.3 only works if every shortcut is defined in one place, and that is
much easier to keep true from the start than to impose later.

How
---

  * ScratchpadLite.Core targets plain net10.0, with no WPF reference. That is
    not a convention to remember; the compiler refuses the alternative, which is
    what keeps the format and font code testable without a window.
  * Everything that costs time at startup is deliberately on the far side of
    ContentRendered: fonts, recovery, spell check, the format libraries and the
    timers all start after the first frame, and App.OnStartup carries a comment
    saying so, because that is where the budget gets lost.
  * The format registry keeps names and extensions in a static table and creates
    each handler through Lazy<T>, so building an Open dialog filter loads no
    format package and .NET never pulls in the Open XML SDK at startup.
  * --measure-startup needed one thing the blueprint did not mention: this is a
    WinExe, so it has no console and a plain Console.WriteLine goes nowhere.
    It attaches to the console of the process that launched it, which is what
    lets build.ps1 read the number; a double click fails the attach harmlessly
    and the value is still in the log.
  * One deviation from Section 11.1, noted in the .csproj: SupportedOSPlatform-
    Version 10.0.17763.0 is rejected on a bare net10.0-windows TFM, whose
    TargetPlatformVersion is 7.0. Raising it means a net10.0-windows10.0.x TFM,
    which pulls in the Windows SDK WinRT projections. Nothing here uses WinRT -
    spell check comes through WPF and the dark title bar through a DWM P/Invoke -
    and Section 2.1 says a dependency has to earn its place, so the TFM stays
    lean and the Windows 10 1809 floor is declared in app.manifest and the
    README instead.
  * A placeholder app.ico is generated into Resources; it is a plain mark and
    is meant to be replaced.
  * Two dialog classes are named ParagraphDialog and PageSetupDialog rather than
    Paragraph and PageSetup, because those two names are already taken by WPF
    and by the IR respectively, and a type that shadows either one is a trap.


The three-way publish measurement (Section 11.1)
------------------------------------------------

Run with `build.ps1 -MeasureVariants` on this PC. Each number is the median of
runs 2 to 5 of --measure-startup; run 1 is reported separately because it also
prepares the fonts.

    Variant                                     exe size    startup
    1  compression off, native libs in the exe   141.2 MB     524 ms
    2  compression off, native libs beside it    133.3 MB     559 ms
    3  compression on (comparison only)           63.5 MB     746 ms

Kept: variant 1, which is what the .csproj already had.

It is the fastest and it is also the one that keeps the app a single file, so
there was nothing to weigh up and nothing to ask about. Variant 2 saves 8 MB,
is 35 ms slower, and scatters native DLLs beside the .exe; it loses on both
counts.

Turning compression on is the real trade: it cuts the .exe from 141 MB to
63 MB, and costs 222 ms, which is 42% of the startup budget for a file size
nobody sees after the first unzip. Section 2.1 says speed wins when speed and
size conflict, and this is what that rule was written for.

The shipped zip is 58.5 MB either way, because Compress-Archive compresses the
uncompressed .exe about as well as the single-file packer would have. That is
the whole argument against variant 3 in one line: the download is the same size
and the app opens slower.
