unreleased  -  2026-11-14  -  The package licence check is gone; Dependabot watches NuGet
--------------------------------------------------------------------------------

No version number: nothing here reaches the .exe.

What
----

The licence check is removed from the project's rules, at the user's request.

  * Section 0 of the blueprint used to read: "Before adding any package, check
    its license and how recently it was updated, and record it in
    THIRD_PARTY_LICENSES.txt. Allowed licenses: MIT, BSD, Apache 2.0, MS-PL,
    SIL OFL. Anything else, or a package with no release in 2 years, ask me
    first." It now reads: "Before adding any package, check how recently it was
    updated; if it has had no release in 2 years, ask me first." The staleness
    check and the ban on paid or licence-key libraries stay; the licence check,
    the allowed list and the requirement to record a licence are gone.
  * Both copies of the blueprint were edited - docs\ and the one in Downloads -
    because they were identical and the Downloads copy is the one a later
    session would copy from. They are still identical.
  * The aside at Section 6.6.5 that said to record Google's woff2 licence now
    just names the licence.
  * THIRD_PARTY_LICENSES.txt no longer restates the allowed-licence policy in
    its header.
  * CLAUDE.md gained "Adding a NuGet package", which says plainly that there is
    no licence check any more and not to reinstate it from an older copy of the
    spec.
  * .github/dependabot.yml now watches NuGet as well as the actions: monthly,
    with the three shipped packages and the four test-only ones grouped into
    separate pull requests.

Why
---

The user's call, and the rule was theirs to drop: it was a process they had
imposed on themselves, and this project does not take a package often enough
for an allowed-list to be earning its keep. It was also the thing that made a
Dependabot NuGet pull request expensive - a version bump would have arrived
carrying a licence review that a version bump cannot actually change, since the
licence of a package does not move when its version does.

One thing does not go away with it, and the shipped file now says so instead of
stating the policy. THIRD_PARTY_LICENSES.txt travels inside the zip, and every
licence in this build - MIT for the Open XML SDK, System.IO.Packaging, the .NET
runtime and WPF, BSD-2 for Markdig, BSD-3 for the Adobe Glyph List - asks that
its notice travel with the software. That is an obligation of those packages
rather than a rule of this project's, so removing the project's rule does not
remove it. The file stays, and new packages still get listed in it. What is
gone is the gate in front of adding one.

The two groups on the NuGet side are not symmetry for its own sake. A bump to
the Open XML SDK can change what a saved .docx contains, which is worth reading
carefully against the fidelity matrix; a bump to the test runner is a different
kind of risk, and the two do not read well in one diff.

How
---

Scope was checked rather than assumed, because "licence" appears about thirty
times in the blueprint and most of them are a feature rather than a rule. Three
separate things share the word:

  * the package licence check - a process rule, and the thing removed;
  * font licensing - FONT_LICENSES.txt, its generator, the Font Report's
    licence column, FontInspector reading licence strings and fsType out of raw
    sfnt bytes, and the flags for "not for redistribution". That is shipped
    behaviour with code, tests and a QA step behind it, so it is untouched;
  * the shipped notice file existing and being copied into the zip, which
    build.ps1 does and ReleaseAuditTests asserts. Untouched.

Nothing in the test suites reads the blueprint - the tests that mention it
encode its values in C# - so there was nothing to update there, and no test
asserts anything about package licences. 456 + 531 still pass.

The NuGet entry names the four project folders one by one instead of pointing
Dependabot at the solution. ScratchpadLite.slnx is the new XML solution format,
and whether Dependabot can read it yet is not a question worth depending on.

One line was left deliberately, and is worth a second opinion: the last line of
THIRD_PARTY_LICENSES.txt still asks that each test fixture font's source and
licence be recorded in tests/Fixtures/Fonts/README.txt. It was left because it
is about fonts rather than packages and about files that are never shipped, but
it is a licence-recording requirement and it can go the same way if the user
wants it to.

unreleased  -  2026-11-14  -  Build: pinned actions, Dependabot, CLAUDE.md
--------------------------------------------------------------------------------

No version number: nothing here reaches the .exe.

What
----

  * .github/dependabot.yml, new. Monthly github-actions updates, all of them
    grouped into one pull request, five open at most.
  * The four actions in build.yml are pinned to commit SHAs instead of
    floating major tags, each with its release in a trailing comment:

        actions/checkout             3d3c42e5  # v7.0.1
        actions/setup-dotnet         0f4a354d  # v6.1.0
        actions/upload-artifact      cf430e03  # v7.0.2
        softprops/action-gh-release  8a0cd651  # v3.0.4

  * CLAUDE.md, new. The rules that are not a session's to relax, the two
    exclusions that keep the blueprint unpublished, when to bump the version
    and when not to, why the SHAs must not be "tidied" back into @v7, and the
    test convention that a test never asserts anything about the machine it
    runs on.
  * build.ps1 no longer puts the blueprint in the source zip.

Why
---

A tag is a pointer, not a version. "actions/checkout@v7" runs whatever the v7
tag points at when the build starts, and whoever has write access to that
repository decides what that is. In March 2025 somebody with write access to
tj-actions/changed-files repointed every version tag at a commit that printed
the runner's secrets into the build log, where they are public on a public
repository. Around 23,000 repositories ran it. None of them had changed a line.

That risk is worth more here than the floating tags were:

  * this job holds a contents: write token, and
  * it builds an unsigned .exe that users download from the releases page.

With no code signature, a swapped zip has nothing to give it away. The SHA-256
in the release notes is the check that would catch it, and it only works if the
zip was built where the hash was computed.

A SHA pin cuts the other way, though, and that is why dependabot.yml came
first rather than as a footnote. A floating tag heals itself under neglect: the
fixes arrive whether or not anybody is paying attention. A pinned SHA rots
under neglect - it is frozen at a version that is safe today and will have a
known hole in it eventually. Pinning without something that remembers trades a
small exotic risk for a large certain one, which is a worse deal than not
pinning at all. Dependabot runs on GitHub's side, so it does not depend on
anybody holding a runtime deprecation in their head between one month and the
next, and it understands SHA pins: it rewrites the hash and the trailing
comment together.

CLAUDE.md is the same problem one level up. An editor session starts with no
memory of the last one, so a decision that lives only in a conversation is a
decision that gets quietly undone - a future session sees four 40-character
hashes, reads them as clutter, and floats them back to @v7 believing it is
tidying up. The repository has to be the memory. The file is also where the
things that have survived ten phases are written down plainly: the startup
budget, the fonts folder, C# and PowerShell only, Core never referencing WPF.

How
---

The SHAs were not taken on trust. For each action: the floating major tag and
the latest release were both resolved to a commit, and the two agreed, so
pinning freezes exactly the code that had just passed a green run rather than
quietly moving to something else. Then each SHA was compared against its
repository's default branch and came back "identical" or "behind" with
ahead_by 0 - that is, an ancestor of the branch head rather than a commit
sitting outside the history, which is what a repointed tag looks like.

The blueprint exclusions were a leak found while writing CLAUDE.md, not a
tidy-up, and both doors were open rather than one. The blueprint was copied
into docs/ this morning; the .gitignore rule meant to keep it out of this
public repository was written at the same time and never committed, so it
existed only in this PC's working tree. And the source zip is built by walking
the file system rather than by asking git, and is attached to a public release,
so even a committed .gitignore would not have stopped it going out that way.

Nothing was actually published. v1.10's source zip was built the evening
before the blueprint arrived, and the last commit predates it too. That is
timing rather than protection: the next commit or the next zip would have
carried it. Both exclusions are committed now - the .gitignore rule and the
build.ps1 one - and CLAUDE.md says not to remove either.

unreleased  -  2026-11-14  -  Build: the workflow's actions moved to Node 24
--------------------------------------------------------------------------------

No version number, because nothing in the app changed. This section is here
because every change gets written down, and the four lines it changed are in
.github/workflows/build.yml only - not in anything that ends up in the .exe.

What
----

The four actions the build workflow uses, moved to their current majors:

    actions/checkout            v4 -> v7
    actions/setup-dotnet        v4 -> v6
    actions/upload-artifact     v4 -> v7
    softprops/action-gh-release v2 -> v3

Why
---

GitHub is retiring Node 20 from the Actions runners. The v1.10 tag build and
the run on main both ended with:

    Node.js 20 is deprecated. The following actions target Node.js 20 but are
    being forced to run on Node.js 24: actions/checkout@v4,
    actions/setup-dotnet@v4, actions/upload-artifact@v4

"Forced to run" is the runner papering over it. When that shim goes, the
workflow stops, and the way that failure would arrive is a tag build: push
v1.11, get nothing built and nothing attached to the release. Fixing it while
it is a warning is cheaper than fixing it while it is a tag that produced no
zip.

The fourth action is the reason this was worth doing carefully.
softprops/action-gh-release@v2 is also Node 20, and it was NOT in that warning
list - because the step that uses it is skipped on anything but a tag, so the
run on main never loaded it. It is also the only action here that runs with
contents: write, on the one build that publishes a release. It would have
warned on the next tag and broken on the one after.

How
---

The majors were read before they were taken, not assumed:

  * checkout v5 is the Node 24 move, v6 writes credentials to a separate file,
    v7 blocks checking out a fork's PR under pull_request_target and
    workflow_run. This workflow has neither trigger, so v7 is a free upgrade.
  * setup-dotnet v5 is the Node 24 move and drops the installers for older
    .NET lines; v6 is an ESM port. 10.0.x is unaffected.
  * upload-artifact needed v6, not v5: v5 "had preliminary support for Node 24,
    however this action was by default still running on Node.js 20", so a bump
    to v5 would have left the warning in place. v7 adds an archive parameter
    that defaults to true, so the dist/*.zip glob behaves as before.
  * action-gh-release v3 is a pure runtime move to Node 24. Its v2 line stays
    pinned at 2.x for runners that need Node 20; this one does not.

All four are floating major tags, which is what they were before. Pinning them
to commit SHAs would be stronger - a floating tag can be moved under you, and
one of these is a third-party action holding contents: write - but that is a
separate decision about this repository's threat model rather than part of a
deprecation fix.

v1.10  -  2026-11-13  -  Phase 10: fonts inside documents
--------------------------------------------------------------------------------

What
----

Section 7.4, the optional last phase: a .docx or .odt can carry the fonts it
uses, so a document written in a font from the fonts/ folder looks the same on
a PC that has never seen it.

  * The setting, in Preferences under Saving: "Embed fonts from the font
    folder when saving". Off until it is turned on.
  * DOCX. Each face goes in its own font part, obfuscated as ECMA-376 section
    17.8.1 describes, referenced from a w:font entry by r:id and font key.
    settings.xml says w:embedTrueTypeFonts, without which Word reads the
    document, sees no instruction to embed and drops the fonts on its next
    save.
  * ODT. The font file goes in Fonts/ and is declared in
    office:font-face-decls with svg:font-face-uri, in content.xml and
    styles.xml both, and listed in the manifest. ODT does not obfuscate;
    that is the format's decision.
  * Reading both back. A document that arrives carrying fonts unpacks them to
    data/font_cache/embedded/<document>/ and loads them for that tab alone:
    they do not appear in the font picker, they cannot be applied to anything
    else, and two documents carrying different fonts under one name do not
    collide.
  * A document that already carries fonts keeps them on save, whatever the
    setting says. The setting decides something narrower: whether a font from
    this PC is added to a document that did not have one.
  * Three rules decide what may travel: only fonts from the fonts/ folder,
    only where the font's own fsType allows it, and never a font converted
    from Adobe Type 1. What is left behind is named in the status bar with the
    reason.
  * Recovery.Forget existed since Phase 8 and was never called, so a closed
    tab's recovery file sat there until the next clean exit. Closing a tab now
    forgets it, which is what the method was written for.
  * 987 tests passing (456 in Core, 531 in App), up from 907.

Measured on this PC, publishing the release build:

    warm startup   683 ms and 759 ms, two publishes of the same code, with
                   spreads of 622-694 and 676-931. Phase 9's nine-run median
                   was 692 ms. Unchanged, in other words: nothing was added
                   before the first frame, and nothing here runs at all
                   unless a document carries fonts or the setting is on.
    budget         1000 ms warm.
    idle memory    158.9 MB working set, 86.9 MB private
    .exe           170.2 MB, up 0.2 MB from v1.9
    zip            68.3 MB
    source zip     0.67 MB, 213 files

The phase gate is "a .docx with a fonts/ font opens in Word on another PC and
shows that font". Word turns out to be installed on this one, so most of that
was answered here rather than left for a second machine.

A real font - Wingdings, for outlines nothing could be mistaken for - was
given a family name no PC has, put in a font folder, prepared by the real
font pass, and embedded in a .docx through the real save path. Then Word was
asked to open it:

    opens with no repair prompt   yes
    w:embedTrueTypeFonts read     yes
    font on the text              "Scratchpad Embed Test"
    line width as laid out        181.5 pt
    the same text set in Arial    245.5 pt

The last two lines are the ones that matter. Word is laying the line out with
the embedded font's own advance widths, on a PC where that family is not among
the 513 installed: had it failed to load the font and substituted, the two
numbers would have agreed. What is left for a second PC is the look of it on
the page, which is a question for eyes.

Why
---

The setting is off by default for the same kind of reason AutoSave is. Turning
it on copies somebody else's font file into a document that may be sent
anywhere, which is a decision about a licence rather than about a file format,
and not one to make on a user's behalf.

The three rules are all somebody else's decision rather than this program's. A
font that came with Windows is on the PC at the other end already, and copying
Microsoft's fonts into a document would break their licence for nothing. The
fsType flag is the foundry's statement about its own font, so Restricted is
refused, and so is preview-and-print, which would make the document read-only
in Word - a worse outcome than a substituted font. A converted Type 1 font is
refused because what would travel is this program's conversion rather than the
file anybody licensed, which is also why Section 6.6.4 stamps the conversion
preview-and-print.

Where a font contradicts itself - Restricted and Editable both set, which the
specification says cannot happen and files do anyway - the stricter reading
wins. Reading it the other way would be this program choosing the answer it
preferred about somebody else's licence.

A document that arrives carrying fonts keeps them. Stripping them out when the
setting is off would be deciding on the user's behalf that their document
should stop looking the way it looks everywhere else, and they would find out
about it on somebody else's PC. Only families the document still uses travel,
so a font kept for text that has since been deleted is dropped.

The fonts a document brings are kept apart from the fonts/ folder's, per
document, rather than merged into one list. Two documents can carry different
fonts under the same family name, and whichever was opened second would
otherwise take the name for both. It also keeps an embedded font out of the
picker, which is right: it is not something the user installed.

The faces are unpacked to files rather than loaded from memory because that is
how WPF loads a font - from a URI. They are tidied at the next launch rather
than when the tab closes, because WPF holds a font file open for as long as
the family is registered and will not let go until the process ends; a folder
left by a previous run belongs to nobody, so that is the moment it can go.

Section 7.4 asks for the refused fonts to be listed "in a save warning". They
go to the status bar instead, where the AutoSave skip reasons already go. The
save warning is a modal dialog, and this is a condition that does not change
between saves: a licence that forbids embedding will forbid it again in two
minutes, and a dialog every time would train the user to click it away. It is
said once per font per session, which is saying it.

How
---

The obfuscation key was measured, not read. ECMA-376 says to "reverse the
order of the bytes in the GUID (i.e. Big Endian ordering)", which can be read
three ways, and the implementations published on the web split between two of
them with each saying the other is wrong. Reading the sentence harder was not
going to settle it, and neither would a round-trip test, which only proves
this program agrees with itself.

What settled it: XpsFont.ObfuscateFontData, Microsoft's own implementation of
the same obfuscation for XPS, which ships in ReachFramework with the Windows
Desktop runtime. Three candidate orderings were run against it and one matched
- the GUID's big-endian bytes reversed, so AABBCCDD-EEFF-0011-2233-445566778899
gives 99 88 77 66 55 44 33 22 11 00 FF EE DD CC BB AA - applied twice, to
bytes 0 to 15 and again to 16 to 31. A test in the App suite holds the two
implementations together, because a lucky agreement nobody checks is a
coincidence waiting to break. Core cannot reference WPF, which is why that
test cannot live beside the code it tests; Core's own suite asserts the key
bytes that measurement produced.

The two implementations part company in one place, and deliberately. Microsoft's
walks off the end of a file shorter than the thirty-two bytes it scrambles: it
is written for fonts, and a font is never that short. This one is also used on
bytes that arrived inside somebody else's document, where "it cannot be that
short" is not something that can be assumed, so it stops at the end of the
array and lets the reader's own check refuse the file. There is a test for
that difference.

Everything on the reading side is treated as hostile (Section 7.5): the number
of faces is capped at 64, each one is size-checked before it is read, an ODT
href that climbs out of the package is refused, and a face that cannot be
unscrambled is passed over with a warning rather than stopping the document
opening. The check that it still looks like a font after the key is applied is
worth more than it looks - it is the one thing that would catch the
obfuscation being wrong, which otherwise shows up as a tab of unreadable text.

Two things the tests settled that the documentation would not have:

  * Windows' own core fonts are Editable rather than Restricted - arial,
    segoeui, consola, times and wingdings all report fsType 0x0008. That does
    not change what this program does with them, because they are refused for
    being Windows fonts rather than for their rights, but it means the
    end-to-end test of a real prepared font takes the embedding path rather
    than the refusing one.
  * The Open XML SDK's font parts are reached through FontPartType.FontOdttf,
    which produces /word/fonts/font.odttf with the content type Word uses.
    The SDK's FontPartType is a static class of PartTypeInfo values rather
    than an enum, which is not what the shape of the name suggests.

IFormatHandler.Write grew a WriteOptions parameter rather than the handlers
growing a property. The handlers are shared - FormatRegistry makes one of each,
lazily - and two tabs can be saving at the same moment, so per-save state on a
shared instance is a race waiting to happen. A style sheet can live on the
handler because it is the same for every document; the fonts to embed are this
document's. ReadResult gained the fonts the same way, beside the document
rather than inside it: the IR describes what a document says, and the IR is
what the recovery copy is serialized from - font bytes in there would mean
megabytes written every two minutes.

That last point has a consequence worth stating plainly, and it is in the
guide as limitation 8: a document restored after a crash has lost whatever
fonts were embedded in it, because recovery keeps the text rather than the
file. The original file on disk still has them.

--------------------------------------------------------------------------------
v1.9  -  2026-11-12  -  Phase 9: the release
--------------------------------------------------------------------------------

What
----

The release pass: the QA checklist, the documents, the source bundle - and the
three menu items that were still greyed out. A release with a dead menu item in
it is not a release, so they were built first.

  * Format, Paragraph (ParagraphDialog). Alignment, left and right indent,
    first line, space before and after, and line spacing, in one dialog and one
    undo step. Indents in inches and spacing in points, which is what every
    other word processor shows. A blank box means "leave that one as it is", so
    a change to several paragraphs at once does not flatten the differences
    between them; where the selected paragraphs disagree, the box starts blank.
    Line Spacing, Custom goes to the same dialog, and so does the toolbar's
    line-spacing menu.
  * Insert, Special Character (SpecialChars). A grid of characters in the font
    at the caret, a Unicode range at a time, with the ones used lately kept at
    the top and remembered in settings. It shows only the characters the font
    can actually draw, asked of the font's own character map. The window stays
    open while characters are picked, and the insertion is done by the window
    rather than by the dialog, so there is still one piece of code that writes
    to the document.
  * View, Show Formatting Marks (FormattingMarks). A pilcrow at the end of
    every paragraph, a dot between words, an arrow across a tab, a return mark
    at a line break, and a ring rather than a dot for a non-breaking space.
    Phase 1 left this disabled because WPF has nothing for it; it is an overlay
    over the text that reads where each character landed.
  * QA_CHECKLIST.md: all twenty-two checks in Section 10.2, each one saying
    whether a test covers it, whether it was run here against the built .exe,
    or whether it needs a person and a screen - and for the tested ones, which
    test.
  * The source bundle Section 0 asks for at every phase gate, which no phase
    had produced: build.ps1 now writes dist\ScratchpadLite-v1.X.zip, the whole
    source tree with a FILES.txt listing every file in it.
  * New tests: the manifest and publish settings the release depends on, EOT
    refusals, what WPF really does with a variable font, and the three features
    above.
  * 907 tests passing (387 in Core, 520 in App), up from 854.

Measured on this PC, publishing the release build:

    warm startup   683 ms, the median of runs 2-5, spread 669 to 728.
    budget         1000 ms warm. Cold needs a reboot and is yours to check;
                   the budget is 2.0 s.
    idle memory    159.3 MB working set, 86.3 MB private
    .exe           170.0 MB, up 0.1 MB from v1.8
    zip            68.2 MB
    source zip     0.63 MB, 205 files

Startup was measured three times over two publishes of the same code, because
the first answer looked like a regression and was not one: 726 ms (median of
runs 2-5), then 692 ms (median of nine runs, 666 to 700), then 683 ms (median
of runs 2-5, 669 to 728). The spread inside a single run of five is about 60
ms, which is wider than any of the differences between those three numbers and
wider than the gap from v1.8's 695. So build.ps1 now prints the spread beside
the median: a bare number invites a hunt for a cause that is not there.
Nothing was added before the first frame this phase - the marks overlay is one
element in the editor's own XAML and paints nothing while it is switched off.

The end-to-end checks in QA_CHECKLIST.md were run against this build:

    no runtime     ran with DOTNET_ROOT pointed at nothing and dotnet taken
                   off the PATH: 677 ms to the first frame
    hand-off       a second launch with a file passed it to the running copy
                   and exited; the log shows the first copy opening it
    read-only      with the program folder denied new files, the app ran
                   (686 ms), wrote nothing beside the .exe, and put its data
                   in %LOCALAPPDATA%\ScratchpadLite
    scaling        the editor rendered at 96 and 192 DPI; the text and the
                   marks are drawn at the higher resolution, not scaled

Why
---

Three menu items had been greyed out since the phases that were meant to build
them - two of them without being reported at the time, which was a gap in those
phase reports. The release is the last point at which that can be put right,
and every one of the three is in Section 8.1's menus, so leaving them would
have meant shipping a program whose menus describe features it does not have.

The Paragraph dialog needed one new thing underneath it: ApplyParagraph, which
sets everything the dialog changed inside a single change block. The older
helpers - SetAlignment, SetIndents, SetSpacing, SetLineSpacing - each open a
change block of their own, which is right for a toolbar button and wrong for a
dialog with seven fields, because it would take seven Ctrl+Z to undo one OK.

The blank box is the other half of it. A dialog that shows a number for every
field has to invent one when the selected paragraphs disagree, and whatever it
invents gets written to all of them the moment OK is pressed. A blank says "they
differ" on the way in and "leave them alone" on the way out, and those are the
same statement.

The character grid shows only what the font has because the alternative is a
grid of empty boxes, every one of which would insert a character the document
cannot show. The ranges are each a single Unicode block or less, so the grid is
a few hundred buttons rather than tens of thousands, which is what lets it be a
plain WrapPanel: WPF has no virtualizing wrap panel, and writing one for a
dialog that is opened occasionally would be a lot of machinery for nothing.

Formatting marks are drawn rather than inserted, which is the only honest way:
they are not in the document, so they cannot be saved, printed, selected or
deleted. The overlay sits in the same grid cell as the text box rather than in
an adorner layer, because the adorner layer belongs to the window and is not
clipped by the editor's scroll viewer - marks would have been painted over the
toolbar the moment the document scrolled.

Only the visible text is marked. That is not an optimisation, it is what makes
the feature possible: each mark costs a GetCharacterRect, which is a question
to the layout engine rather than a lookup, and a three-hundred-page document
has a million of them. Working out which text is on screen costs two questions
in total, so a paint is proportional to the window rather than to the file.

How
---

Six things the tests found, four of them before the feature was finished.

  * The first version of the visible-range check asked where each paragraph
    ended, so a paragraph taller than the window - its start above the top of
    the screen and its end below the bottom - was skipped entirely. The marks
    vanished exactly when there was most to mark. It now asks whether the
    paragraph reaches the visible range at all.
  * The last paragraph on screen lost its pilcrow. The position that bounds

Why
---

Recovery and AutoSave are one feature in most word processors and two here,
because they answer different questions. Recovery answers "the power went out";
AutoSave answers "I forgot to press Save". Recovery can therefore be on for
everyone and for every document, since it never touches a file anybody owns.
AutoSave cannot, because writing someone's file without being asked is a thing
to be asked about - so it is off, it has a switch where it can be seen, and it
declines rather than guessing in four cases that all come down to the same
thing: a save that would not be the save the user would have made.

The whole of recovery rests on one question: how does a launch tell "a copy is
running right now and those are its working files" from "a copy died and those
are somebody's unsaved work"? A timestamp cannot answer it. A process id cannot
either, because Windows reuses them, and a folder naming a pid that now belongs
to something else reads as live. The answer is a lock file held open with
FileShare.None for the whole life of the process: Windows releases it when the
process ends, however it ends, and a folder whose lock file can be opened is a
folder whose owner is gone. Nothing has to be cleaned up by the thing that
crashed, which is the only kind of cleanup a crash can be relied on for. The
test for it kills a real process holding a real lock rather than disposing a
handle and calling that the same event.

AutoSave does not have a save of its own. It decides whether and when, and the
window then calls the same SaveAsync a menu click calls. A second save path
would be a second place for the atomic write, the format warning and the
changed-on-disk check to drift apart, and the one nobody clicks is the one that
would rot. What the AutoSave flag changes is only the asking: it opens no
dialogs, because a dialog raised by a timer appears while the user is typing in
another program. That is not skipping the checks - the three questions those
dialogs would have asked were all answered by AutoSave.Check before SaveAsync
was called.

The printed document is a copy, through DataFormats.XamlPackage. A FlowDocument
has one set of page settings, and printing needs the printer's rather than the
editor's, so printing the document itself would mean reflowing what the user is
looking at and then putting it back. The package form of the clipboard format
rather than plain XAML, because the package carries the images as parts beside
the markup while plain XAML leaves a reference behind and prints a hole.

Preferences reads a Settings and gives back a new one, changing nothing itself.
The window applies what comes back, which is the only way the theme, the open
editors and the file on disk end up agreeing. Numbers are clamped where a clamp
has an obvious right answer and refused where it does not: an interval of 2
seconds becomes 15, because somebody typing 2 wants it as often as possible,
while an interval of "soon" has to be typed again.

The single-instance check fails open everywhere. A mutex that cannot be
created, a pipe that cannot be reached, an identity that cannot be read: each
of them ends with this copy showing its own window. An application that starts
and silently exits is indistinguishable from one that is broken, and that is a
worse outcome than two windows. The mutex is claimed before the setting that
says whether to honour it is read, which looks backwards and is not: claiming
is one call on the startup path, while reading settings.json to find out
whether to bother would put a file read in front of every launch for a setting
almost nobody changes. So the first copy pays for a mutex and nothing else, and
only a second copy - which is about to exit anyway - pays for the read.

Both names carry a hash of the program folder, so a copy on a USB stick and a
copy in Documents are separate applications, which is what a portable app
needs. The pipe name also carries the user's SID and the pipe is created with
an ACL for that user alone: a named pipe is visible to the whole machine, and
without those two things another signed-in user could hand this process a list
of files to open. What arrives over it is treated as data from another process
- the count and the length of each line are capped, and the window checks that
each path is a file that exists before opening it.

How
---

Four bugs and two findings came out of the new tests.

  * The IR could not be read back at all. System.Text.Json writes an
    IReadOnlySet<string> happily and refuses to read one: "the collection type
    is abstract, an interface, or is read only, and could not be instantiated
    and populated". SpDocument.FontsUsed is one. This had been true since Phase
    4 and nobody had noticed, because nothing read the IR back - the format
    handlers all parse their own files into IR and serialize IR out, and
    SpDocument itself had only ever been written. Crash recovery is the first
    feature in the application that writes IR JSON and then reads it, and it
    failed on its first test. Fixed with a converter in Core, which also takes
    a JSON null as an empty set rather than letting a null into a property
    whose type says it is never null, and writes the names sorted so two writes
    of one document give the same bytes.
  * A second Claim() in one process threw away the first one's mutex handle.
    The field was assigned before the created-new flag was checked, so the
    handle a successful earlier claim was holding was replaced and then
    disposed. The application only ever claims once, so this would never have
    been seen in use - the test that claims twice is what found it.
  * An abandoned recovery folder with nothing in it was never deleted. A run
    killed after saving everything leaves a lock file and no documents: the
    clean-exit path never ran, and the next launch finds nothing in it to
    offer, so it stayed for ever and one more arrived with every crash. The
    launch now tidies away abandoned folders holding nothing recoverable, and
    leaves any folder with so much as one readable document in it for the
    dialog.
  * Recovery.Claim only caught IOException and UnauthorizedAccessException. The
    data folder can come from a settings file or a command line, so a path
    Windows will not take at all is a thing that can happen, and it threw
    ArgumentException straight out of a safety net. A recovery write that fails
    must leave the application running without recovery, not stop it running.
  * Section 6.17 says a printed FlowDocument comes out in two columns unless
    ColumnWidth is set to PageWidth. On .NET 10 a FlowDocument's ColumnWidth
    starts as NaN, which is one column, and a copy made the way Printing.Clone
    makes one starts there too - so the line is insurance against a document
    that arrives carrying a column width rather than a cure for a default. The
    hazard is real: a control test sets a narrow column width and watches text
    appear in the right-hand half of the sheet. The line stays, and the gate
    test is what would catch the default changing.
  * A laid-out page's text is not elements. The first version of the one-column
    test looked for Glyphs elements in the page's visual tree and found none: a
    printed FlowDocument page draws each line as a GlyphRunDrawing inside a
    visual's DrawingGroup. Looking at the glyph origins is the only way to
    count the columns a FlowDocument used, because the column count is never
    exposed - and it is the test the phase gate actually needs, since reading
    ColumnWidth back would only prove the assignment happened.

Two about the tests themselves.

  * A Markdown file with a table in it loses nothing, because Markdown has pipe
    tables. The first AutoSave test assumed otherwise and failed. The rule is
    what this document uses against what this format carries, not whether the
    format feels simple - so the test now uses coloured, underlined text, which
    Markdown has no syntax for, and there is a second test asserting the table
    case is fine.
  * MainWindowTests built its window with MeasureStartup off. Harmless when the
    only thing past the first frame was font preparation; not harmless once
    that line also claims a crash-recovery folder in the real data directory
    and opens the single-instance pipe. Those tests are about what the window
    parses and lays out, so they now use the measurement flag, which renders
    one frame and starts none of it.

Six menu items stopped being grey: Page Setup, Print, Export as PDF, Recover
Documents, AutoSave and Preferences. A Theory in MainWindowTests asserts each
one is enabled, because a feature can be built and still be unreachable - the
code works, the unit tests pass, and the menu entry stays grey.

Two menu items are still disabled and are not Phase 8's: Format, Paragraph
(with Line Spacing, Custom) and Insert, Special Character. Both were left as
shells in earlier phases without being reported, which was a gap in those
phase reports rather than a decision.

The recovery interval and the AutoSave interval are stored in seconds although
Section 6.13 asks for minutes. The fields already shipped that way in Phase 0,
and seconds is finer than the blueprint asks for rather than coarser; the floor
is 15 seconds rather than the blueprint's 1 minute, because a recovery write is
a walk and a small JSON file, and somebody who would rather lose fifteen
seconds of work than a minute of it should be able to say so. Both defaults are
the blueprint's two minutes.

Why
---

Section 6.12 says not to put the editors in a TabControl, and it is right for a
reason worth writing down. A TabControl keeps one content presenter and
re-creates the content of a tab every time you switch to it. For a RichTextBox
that means a new control each time, and a new control has an empty undo
history and a scroll position at the top. Switching tabs would quietly cost the
user their undo - in the built application only, because nothing about it looks
wrong until you press Ctrl+Z.

So every editor is made once and kept alive in one Grid, and switching tabs
changes which one is visible. The strip above holds nothing but headers.
TabTests.UndoSurvivesATabSwitch is the test that proves it, and it asserts both
that the RichTextBox is the same object afterwards and that Undo still works.

The second decision is how little of the window had to change. Every command
was bound to "the editor" once, in the constructor, through a local variable.
That variable is now a property, Editor, which returns whichever tab is
showing - so a command reaches the active document because the property is read
when the command runs rather than when it was bound. Had it stayed a local, all
of Phase 1 through Phase 6 would have gone on formatting the first tab for ever,
invisibly.

Find has no WPF support at all, and the shape of the engine is the interesting
part. A RichTextBox holds a tree, not a string: the word "formatting" with its
middle emboldened is three Runs, and a search that looked at one Run at a time
would never find it. So the document is flattened first into units - one per
paragraph, list item or table cell - each carrying the plain text plus a list of
segments recording which TextPointer each stretch of that text came from. The
search runs on the string, and every hit is mapped back to a real TextRange.

A match never crosses a paragraph, a line break, a table cell or a picture. That
is deliberate and not a shortcut: a TextRange spanning two paragraphs cannot be
given replacement text without destroying the break between them, so a match
there would be a match that could not be replaced.

Spell check had one question the blueprint asked to have answered rather than
assumed: which languages to offer. There is no managed API. WPF sets the
language on the control and the Windows checker either has a dictionary for it
or quietly has none, so a hand-written list would offer languages that do
nothing. The answer is to ask the component WPF itself talks to -
ISpellCheckerFactory, through about thirty lines of COM declaration - and fall
back to the five languages WPF shipped with if that fails. Tags without a
region are dropped, because Windows lists both "en" and "en-US" and only the
second is something WPF can be given.

Section 6.11 also asked which tag WPF honours for "this is not prose", zxx or
x-none. Both: WPF passes the tag to the Windows checker, which has a dictionary
for neither. zxx is the registered ISO 639-2 code for no linguistic content, so
that is the one used on Code paragraphs.

The performance check Section 6.11 asked for, and what it found
---------------------------------------------------------------

"Open a 300-page document with spell check on. If typing lags, add a setting
that turns spell check off automatically above a size limit, and tell me."

Typing does lag at that size. Spell check is not why. Each line is the time for
one keystroke to settle, measured ten times per case on this PC:

    pages   characters   spell off   spell on
       20       57,150      2.5 ms     1.6 ms
      100      286,695      5.7 ms     4.9 ms
      300      860,321     18.9 ms    18.7 ms
      600    1,721,898     90.2 ms    82.8 ms

Switching spell check on cost between 3 and 62 ms once, and nothing per
keystroke. The spell-on column is, if anything, slightly faster than spell-off,
which means the difference is below the noise. What is expensive at 300 and 600
pages is WPF's rich text control laying the document out, which is the
known limitation already in the user guide.

So the automatic limit was built but is switched off by default. Settings has
spellCheckMaxCharacters, zero meaning no limit, and SpellSupport.Enable honours
it - the switch Section 6.11 asked for is there for anyone who wants it. What is
not there is this app deciding on its own to take the squiggles away from a long
document on a premise the measurement does not support. A test asserts the
default is zero, so a future tidy-up cannot quietly turn it on.

How
---

Five bugs and two findings came out of the new tests.

  * Every single replace threw. TextRange.GetPropertyValue and
    ApplyPropertyValue check what they are given against a fixed list of what
    WPF calls text formatting and throw ArgumentException - "'Underline'
    property is not valid for text formatting" - for anything else. This app's
    underline kind and super/subscript are attached properties of its own
    (Section 6.8), so they cannot go through those methods at all. The ten
    properties WPF accepts go through the TextRange; the three of ours are read
    off the element at the match start and set on the inlines of the
    replacement. A probe run checked all thirteen rather than guessing which
    were allowed.
  * A RichTextBox has no undo history until it is loaded. Not until it is
    created, not until it is visible: loaded, which WPF raises from the
    dispatcher queue. A control added to a window after that window was shown
    accepts text, reports IsUndoEnabled true, and then has CanUndo false for
    ever. The first version of the tab-switch undo test therefore typed,
    switched, undid, and found the text still there - which looks exactly like
    the TabControl bug it was written to rule out, and was not. AppHost.Settle
    now lets WPF finish loading, and says why in a comment.
  * Replace All replaced forwards, so with a replacement longer than the match
    every one after the first landed in the wrong place. It now works from the
    end of the document backwards, where no range is touched before it is used.
    The test that catches it replaces "x" with "yyyyy" four times.
  * A regular expression that matches nothing at all - "b*" - matched at every
    position in the text, so Replace All would have inserted the replacement
    between every pair of characters. Zero-length matches are now dropped.
  * The user dictionary could not be written: the StreamWriter closed the
    stream that FileOps.AtomicWrite still had to flush and rename, so every
    write ended in "Cannot access a closed file". leaveOpen fixes it.
  * Find Previous skipped a match that touched the current one. With "a"
    searched for in "aaaa" the previous match ends exactly where the selected
    one starts, and the comparison was strict, so Previous jumped past it and
    wrapped round to the end of the document instead.

And one about measuring, which cost an hour. Pumping the dispatcher at
Background priority to let a shown window settle never returns: something at a
higher priority - the caret's own blink is the obvious candidate - keeps the
queue busy for ever, so a Background item is never reached. Two attempts at the
performance measurement above hung there and were killed before it was clear
they were not simply slow. Pumping at Loaded priority settles after layout and
returns, which is what the measurement and AppHost.Settle both use.

Two things found that are WPF being WPF rather than bugs here.

  * TextRange.Text on a range that starts at the beginning of a list item's
    paragraph reports the list marker in front of the text, so a match on the
    first word of a bulleted item comes back as "*<tab>needle". The range is
    right - replacing it leaves the bullet alone, which has its own test - and
    only Text draws the marker in. Worth knowing before trusting Text in a
    test.
  * A table selection still cannot be read from Selection (the Phase 6
    finding), and find and replace is unaffected by it, because the engine never
    uses Selection to decide what a match is.

Tabs and the status bar: the toolbars and the counts follow the active editor
only. Every tab raises its own throttled readout, and a background tab finishing
one would otherwise put another document's formatting in the toolbar. Both
handlers check the sender first.

Dark Paper and the page view apply to every open tab rather than only the one in
front, because they are one setting for the application and a half-dark set of
tabs would read as a bug.

Exit with unsaved work cannot be done synchronously: Closing cannot be awaited,
and a close that carried on while the writes were still in flight would be a
close that lost them. So Save All on exit cancels the close, runs the saves, and
closes the window itself when they are done - and leaves it open if one of them
is cancelled.

IncreaseIndentation and DecreaseIndentation commands. That does not work, and
the way it fails is the worst kind: the command reports that it can execute,
runs without complaint, and does nothing to the list. WPF's own list nesting
lives in its Tab key handling rather than in a command, so there is nothing to
call. What IncreaseIndentation does instead is widen the paragraph's margin,
which looks like an indent on screen until the file is saved and the list turns
out to have been flat all along.

So the nesting is written here against the List and ListItem objects: an item
moves into a list inside the item above it, which is the shape the bridge
builds from a file and reads back. Toggling bullets and numbering still goes
through WPF's commands, which do work, with the markers fixed up afterwards.

Two decisions about tables are worth recording.

A WPF table row does not hold one cell per column. A cell with RowSpan 2
occupies its own row and the one below, and the row below simply has one cell
fewer - there is no placeholder. So a cell's column cannot be read off its
index in the row, and every operation needs the table laid out as a grid first.
That is done once, in TableCommands.Grid, rather than six times slightly
differently.

And a table selection cannot be read from WPF's Selection. A selection is a
stretch of a document, and a document reads a table row by row, so dragging
down the left column of a two-by-two table leaves a selection that starts in
the top-left cell and ends in the bottom-right one - indistinguishable from
selecting the whole table. Merging what that describes would quietly merge four
cells when two were chosen. The editor therefore records which cell the pointer
was in when a drag began and when it ended, and a merge uses those two corners.
A keyboard selection has no drag and falls back to what WPF reports, which is
recorded as a limitation in the user guide.

Pictures keep their original bytes rather than being re-encoded on each save,
so a photograph saved ten times is not ten generations of JPEG, and the bytes
are shared between copies: a logo in forty places costs one array. The key is
the SHA-1 of the content, which is a content key and not a security decision -
a collision would mean two pictures sharing a buffer they are identical to
anyway.

The link rule is the security boundary of this phase. A document is untrusted
(Section 7.5), and a hyperlink in one is a line of text asking this program to
run something. http, https and mailto can only reach a browser or a mail
client, so they open straight away. Everything else - file:, a UNC path, a
custom scheme some other application registered - is shown to the user with its
full address first, because the text of a link and its target can say
completely different things, and that is exactly how a document talks someone
into opening something. The decision is a separate function from the dialog
that acts on it, so the rule itself is tested.

How
---

Seven bugs the new tests found, every one of them something a user would have
hit on the first afternoon.

  * Pressing Tab in a list threw the caret to the top of the document. Moving
    a ListItem between collections invalidates every TextPointer inside it, and
    WPF then drops the caret at the start of the document. The paragraph object
    survives the move, so the caret is remembered as a paragraph plus an offset
    and put back.
  * Enter on an empty list item never ended the list. Two separate reasons, and
    either alone was enough: WPF leaves an empty Run behind when it splits a
    paragraph, so "no inlines" is never true; and TextRange.Text over a
    paragraph includes its break, so an empty paragraph measures two
    characters. The emptiness test now reads the runs.
  * Selecting a word and pressing Ctrl+K replaced the word with the URL. With
    no display text given, the address was used as the text even when there was
    a selection to keep.
  * Changing a link's text destroyed the link. Assigning to a TextRange over a
    Hyperlink's content deletes the content and inserts plain text in its
    place, and the Hyperlink goes with it - silently. The inlines are replaced
    instead.
  * Select All then Ctrl+K made no link at all. A Hyperlink is an inline and
    cannot span paragraphs, and its constructor given two pointers that do
    produces nothing, with no exception. The range is clamped to the paragraph
    the selection starts in.
  * Edit Link and Remove Link were greyed out immediately after making a link,
    because the caret sits just after it and its parent is then the paragraph.
    A caret beside a link now counts as in it, the way it already did for
    pictures.
  * An ODT table always came back with its borders on. ODT has nowhere to put a
    border but a cell's automatic style, and the writer only wrote a style for
    shaded cells - so there was nothing for the reader to read, and it returned
    true regardless.

The test harness needed work of its own, and the lesson generalises. A detached
RichTextBox is not a working editor, and the ways it falls short are quiet:
Selection.Select does nothing, so a test that selects text and formats it
formats nothing; and WPF's editing commands report CanExecute false without
keyboard focus, so Execute returns having done nothing. AcceptsTab matters too -
without it the indentation commands will not run. AppHost.InFocusedEditor now
hands out an editor focused inside a shown window, configured the way
EditorView.xaml configures its own, because a test on a differently configured
control is testing something the user never sees.

Ctrl+Shift+8 and Ctrl+Shift+7 are the list shortcuts, as Section 8.3 says, and
WPF's own Ctrl+Shift+L and Ctrl+Shift+N are removed from the editor's bindings -
both because two shortcuts for one action is one too many, and because the raw
commands would bypass the marker fix-up.

Capabilities gained no new flags this phase: lists, tables, images and links
were already in the set, because the formats could already carry them. What
changed is that the editor can now produce them.

Why
---

Three formats, three different reasons for the shape of the code, and the
reasons are worth recording because they are not symmetrical.

ODT is hand-written because nothing free and maintained covers it, and because
the part of ODT this app needs is a zip of XML - which .NET already has.
Markdown is read with Markdig and written by hand: parsing Markdown properly is
genuinely hard and Markdig is the standard answer, while writing it is a matter
of choosing what to escape, and that choice is the whole quality of the output.
RTF is neither, because Windows already has a converter better than anything
worth hand-writing here - at the price of it being someone else's, with limits
this project cannot lift.

The blueprint's fidelity matrix turned out to be wrong in three places, and the
rule is to say so rather than work around it quietly (Section 0: uncertainty).

  * RTF does not keep super- or subscript. The matrix said it did. WPF's RTF
    writer has no \super or \sub keyword at all: it writes the smaller font
    size the editor draws them with, and nothing else, so the text comes back
    small and on the baseline. Fixing this would mean writing RTF by hand,
    which the blueprint ruled out, so it is recorded instead.
  * RTF keeps only one kind of underline. The matrix said "partly", which was
    right to be cautious: all five kinds survive as a plain underline.
  * RTF is better than the matrix expected everywhere else. Tables keep their
    merges, images survive, and links survive - all three were marked "partly"
    and all three are measured here as working.

The save warning's capability flags could not express the Markdown case. One
CharFormat flag covered bold, italic and underline together, so a Markdown save
either claimed it would lose bold, which is false, or claimed it would keep
underline, which is also false. Underline is now its own flag. The cost is one
more flag; the benefit is that the warning tells the truth, and a warning that
cries wolf is a warning people switch off.

Markdown's images go in a folder rather than into the file because Markdown has
nowhere to put them. That makes a save able to leave files behind, so a save
clears out the images this app wrote last time and leaves everything else in
that folder alone - a README or a picture the user put there survives.

How
---

The ODT writer's XML is written with SaveOptions.DisableFormatting, and that is
a correctness choice rather than a size one. Indenting the XML puts newlines
and spaces inside text:p, and in ODT the text inside a paragraph is content: a
reader folds that whitespace into a single space rather than discarding it, so
every indented paragraph gains a leading and a trailing space. "Hello, world."
came back as " Hello, world. " until this was found, which looks exactly like a
reader bug.

A horizontal rule is a paragraph with a bottom border in both ODT and DOCX, and
recognising one has to happen in the block loop rather than in the paragraph
reader - a function that returns a paragraph can only return a paragraph, and
returning an empty one turned every rule into a blank line.

The ODT reader flattens a style's whole parent chain before reading a run, so a
paragraph of Heading 3 arrives already bold. Bold and italic therefore have to
be subtracted against the app's own style sheet exactly as family, size and
colour already were, or the style's own weight becomes direct formatting on
every run and the next save writes it twice. The same applies to the left indent
that Quote carries. This is easy to miss because the two are not nullable in the
IR, unlike the others.

ODT list definitions are now one per marker rather than one for bullets and one
for numbers, because the numbering format lives in the definition and not on the
list that uses it. A list that does not start at one says so with
text:start-value on its first item.

ODT column widths are automatic styles. There is no width attribute on
table:table-column, so a table whose columns have no styles is a table of equal
columns however the IR describes it - the widths were simply never written
before.

The cell shading styles the ODT writer declares were held in a static
dictionary, drained when content.xml was built. Two documents saving at once
would have mixed their styles. They are per-document now, alongside the column
and list styles.

Markdown escaping is split in two. EscapeInline handles what is syntax anywhere
in a line; EscapeBlockStarts handles what is syntax only at the start of one,
which cannot be decided while a run is being escaped because the run's position
in the line is not yet known. So "# not a heading" goes out as "\# not a
heading" and "1. not a list" as "1\. not a list", escaping the delimiter rather
than the digits. An underscore inside a word is left alone - CommonMark says it
is not emphasis, and a file full of \_ cannot be read as text, which is the only
reason to use Markdown at all.

A Markdown file nested deeper than Markdig's own limit is refused with a
readable message. Markdig throws ArgumentException rather than overflowing the
stack, which is the right thing to do, but an opened file is untrusted
(Section 7.5) and has to come out as a bad file rather than as a bad argument -
otherwise the user is told only that it "could not be opened".

Three bugs in FlowWalker came out of the RTF tests, all the same shape: the
walker assumed the tree its own builder produces, and WPF's RTF reader nests
differently.

  * A hyperlink's content is not always a flat list of runs. WPF's reader puts
    a Span inside the Hyperlink, and the walker looked only at direct Run
    children, so every link in an opened .rtf lost its text entirely - not
    just its target.
  * TextDecorations and Background do not inherit in WPF's property system
    although they render as though they do: a Span marked underlined draws
    every run inside it underlined while each of those runs reports an empty
    TextDecorations of its own. Both are now collected by walking up the inline
    chain, which stops at a hyperlink, whose underline belongs to the link
    style rather than to the text.
  * An image that arrives without original bytes is encoded as PNG from its
    bitmap instead of being dropped. The pixels are there and PNG is lossless,
    so a re-encode is a better answer than a missing picture. This is what
    makes pictures in an opened .rtf survive, and it will do the same for
    pasted ones in Phase 6.

None of the three could have been found by testing the bridge against itself,
which is the general lesson: a round trip through your own code proves only
that it is self-consistent.

Why
---

The IR earns its place in this phase, so it is worth restating what it buys. A
FlowDocument belongs to the thread that owns the window, which means a format
handler that worked on one directly would have to parse a 200-page .docx on the
UI thread, and the window would be frozen while it did. Because every handler
reads and writes plain records instead, the slow part runs on a background
thread and only the final tree build touches the UI. The same split is why
every format handler is tested without opening a window at all.

The other half of the argument is the number of conversions. Five formats and
one editor is five converters through an IR, and would be ten without one -
and each of those ten would have its own ideas about what a heading is.

The rule both sides of the bridge follow, and the reason the round-trip test
can be strict: only direct formatting is written. A run whose font and size
match its paragraph style carries nothing at all. Without that rule a heading
saved to .docx would come out as directly formatted 20-point bold text that
Word no longer knows is a heading - no navigation pane entry, no table of
contents, and no way to restyle it.

How
---

The round-trip test is the one Section 6.4 calls the most important in the
project, and it is 56 cases: every character format, every underline kind,
every paragraph style, every list format, nesting, tables with spans and
shading, images, links, line breaks, page breaks, metadata and page setup,
then one document using all of it at once. It compares
Normalize(Walk(Build(d))) with Normalize(d), and the normaliser is allowed to
discard only what a reader could not perceive: adjacent runs with identical
formatting merged, empty runs dropped, colours upper-cased, sizes rounded to
three decimal places because they make the trip through DIPs and 10.5 pt comes
back as 10.499999999999998. Every other difference is a bug, and it found
three.

  * A list that changed kind silently lost its numbers. The builder gathered
    each run of consecutive list paragraphs into one WPF List element, so a
    numbered list immediately after a bulleted one was folded into the bullet
    list and came back out as bullets. It now starts a new list whenever the
    marker changes, and returns several roots rather than one.

  * A style with no font of its own resolved to whatever WPF felt like. Most
    styles in the sheet leave Family null, meaning "whatever Normal uses", and
    the builder took that literally and set nothing - so the paragraph
    inherited WPF's own default font and the walker read that back as the
    run's font. A heading came out of a round trip in a font nobody had
    chosen. Both sides now resolve it through StyleSheet.FamilyFor.

  * A hyperlink's blue was being recorded as a colour someone chose. A run
    inside a Hyperlink reports the link style's blue as its effective
    foreground, and the walker wrote it into the IR as direct formatting.

And the .docx writer had three of its own, all of which produced files that
looked fine until something checked them properly.

  * WordprocessingML is a sequence, not a set. w:rPr must hold its children in
    one specific order, and a file with w:sz before w:b is invalid even though
    every element in it is legal - Word refuses it as unreadable content. The
    same applies to w:pPr, where spacing comes before indentation and both
    before justification, and to w:style, where pPr comes before rPr. The
    writer now puts them in order from one list per element rather than in the
    order the code happens to produce them. The SDK's own OpenXmlValidator is
    what caught it, which is exactly why Section 7.2 asks for it.

  * Row spans were written with no continuation cells. Word spans rows by
    marking the top cell "restart" and putting a "continue" cell in each row
    below it. The IR leaves those out - a spanned cell simply occupies the
    rows beneath - so the writer has to put them back, and without that a
    two-row span came out of a file as a one-row cell.

  * The Code style's own shading came back as a highlight. A style with
    shading gives every run in it that shading as an effective value, and the
    reader was recording it as something the user had applied.

A note on links: Uri canonicalises, so "https://example.com" comes back as
"https://example.com/". That is the same address by the URI specification
rather than a loss, so IrNormalizer puts absolute URLs through Uri and
compares them that way. Anything that is not an absolute URL - a relative
path, a bookmark, or something a file simply claimed - is left exactly as it
was.

                      699 ms, so still nothing on the startup path.
    index load        10 families from 17 entries in 4 ms
    first run         13 files prepared in well under a second, in the

Why
---

A Type 1 font has outlines, widths and glyph names, and nothing else. No
character map, no metrics tables, no name table in any form an OpenType
consumer can read. So "converting" one is really two jobs: translate the
outlines, and invent - correctly - everything else a modern font is expected to
carry. That is why this phase is mostly SfntTables and the Adobe Glyph List
rather than charstring arithmetic.

The glyph list is the part worth explaining. A Type 1 font says a glyph is
called "eacute"; it does not say that means U+00E9. The only way to build a
cmap is to look every name up in Adobe's published list, which is why 78 KB of
it is embedded. For a symbol or dingbat font the names are the designer's own
invention - "a12", "H18533" - and mean nothing to anybody, so those get a
symbol cmap built from the font's own encoding at U+F020 upwards instead. The
choice between the two is made by counting how many of a font's names the list
recognises, because doing it name by name would give a font with a few
recognisable names a half-working cmap, which is worse than either answer.

Charstrings are converted in two passes - interpret to an outline, then emit -
rather than translated operator by operator. Type 1 has features Type 2 has no
equivalent of: subroutines that return values, flex curves written as seven
separate moves, accented characters that reference two other glyphs by
StandardEncoding code, and division. Going through a plain outline makes all of
that local to the interpreter.

How
---

Three bugs found by testing, each of which had produced something that looked
entirely valid.

  * A C# precedence trap in the CFF writer. "total + 1 switch { ... }" parses
    as "total + (1 switch { ... })", not "(total + 1) switch { ... }", so the
    INDEX offset size came out as the size of the whole INDEX rather than 1 to
    4 - and every offset was then written in that many bytes. A 105 KB
    CharStrings INDEX became 95 MB, and a 140 KB font converted to a 95 MB one.
    Nothing else noticed: the font was still structurally valid, FontInspector
    read it, and the only clue was the size. Both branches now have
    parentheses and a comment.

  * The CFF offsets were written into a copy. The Top DICT holds byte offsets
    to the charset, the CharStrings INDEX and the Private DICT, and they can
    only be filled in once those parts have been measured - so the DICT is
    built with five-byte placeholders and patched afterwards. But the patching
    happened after the DICT had already been wrapped in its INDEX, and
    wrapping copies the bytes. Every offset in the font that shipped was
    therefore zero. DirectWrite's entire diagnosis of this was "Invalid file
    format".

  * The PFA reader swallowed the trailer. A Type 1 program ends with 512 zeros
    and the word "cleartomark", and those zeros are perfectly good hex digits.
    A decoder that reads hex until something is not hex therefore absorbs 256
    bytes of padding into the encrypted data, discovers the problem only at
    "cleartomark", and then - in the first version here - fell back to treating
    the whole section as binary, leaving the private dictionary unreadable and
    the font apparently corrupt. Hex or binary is now decided from the first
    four non-blank characters and then stuck to, and the hex stops at the
    first character that is not one.

One design decision rather than a bug: Type 42's pad-byte rule cannot be
resolved by a reader. The specification says each string in the /sfnts array is
padded to an even length, but nothing records whether a pad byte was added, so
a 2048-byte string could be 2048 bytes of font or 2047 and a pad. Guessing
wrong either way corrupts every table after the first split. Both readings are
tried and the one that produces a font with a readable family name wins -
which needs no guess, and is also why that check has to be the family name
rather than merely "it parsed": the wrong reading parses happily, because the
header and the table directory are in the first chunk and intact either way.

Two notes about testing fonts through WPF, because a day went into them:

  * WPF's font cache is keyed by directory. Load several fonts from one folder
    and the first works while every one after it throws - sometimes
    FileFormatException, sometimes a NullReferenceException from inside
    MS.Internal.FontCache - whether or not the fonts are valid. Each font in
    the tests now gets a directory of its own.
  * Metrics must be read through "new GlyphTypeface(uri)". Going via
    Fonts.GetFontFamilies, then a Typeface, then FormattedText throws
    FileFormatException for a font loaded out of a file - and does it for an
    untouched arial.ttf as readily as for a converted one, which is what
    finally separated the harness problem from the real conversion bugs above.

Smaller things:

  * The PFM field offsets were four bytes out: dfFace is at 105, and 101 is
    dfDevice, which for a printer font reads "PostScript". Every converted
    font was briefly called "PostScript Regular".
  * A .pfm or .afm sitting beside its font used to be reported as "the outline
    file (.pfb) is missing", which sends the user looking for something they
    already have. It now says what it is metrics for, and only reports a
    missing outline when the outline really is missing.
  * SfntTables is the other half of what Section 5.1 called SfntBuilder - the
    table synthesis, as opposed to the container assembly in Sfnt.Build. The
    name was left behind in Phase 2 for the reason recorded there.

Not built in this phase
-----------------------

  * Hints are dropped, which Section 6.6.4 allows. A converted font can look
    slightly soft on screen at small sizes; printing is unaffected.
  * MicroType Express compressed EOT files. That is a Monotype compression
    format with no free implementation, and Section 13 already lists it as
    unsupported. They are refused by name.
  * Multiple Master and CID-keyed Type 1 fonts, as Section 6.6.3 says.

Tested against what
-------------------

Worth being plain about, because the fixtures are what the confidence rests on.

Why
---

The index is the whole performance story, so it is worth being plain about what
it buys. A launch with an unchanged font folder reads one JSON file and
registers every family from the names stored in it - no font file is opened,
nothing is hashed, nothing is copied. WPF reads a font only when text is
actually drawn in it. That is why 687 fonts cost 9 ms and not nine seconds, and
why the startup figure above is the same whether the folder holds nine fonts or
seven hundred.

Fonts are copied into a cache rather than loaded from fonts/ because WPF keeps
a font file open for as long as the family is registered. Loading in place
would mean the user cannot delete, rename or replace their own fonts while the
editor is open. Naming the copy by content hash means an updated font gets a
new cache file instead of fighting over the old one, and two files holding the
same font share one copy.

A font bundle downloaded from the web almost always holds the .otf, the .woff
and the .woff2 of every font. Without duplicate detection the picker shows one
name three times and the cache holds three copies of the same outlines, so the
.ttf or .otf is kept and the rest are marked "Duplicate of ...".

A font in fonts/ wins over an installed font of the same name. Someone who put
a font there did it on purpose.

How
---

Three things were found by measurement rather than by reading, and they are the
substance of this phase.

  * The WOFF2 bounding-box bitmap is padded to four bytes, not one. One bit
    per glyph, and the obvious ceil(n/8) is right for the number of bits and
    wrong for the size of the field: with 2901 glyphs it gives 363 bytes where
    the answer is 364. Every bounding box after it is then read one byte out of
    step, so every composite glyph in the font came out as two halves of its
    neighbours - accented capitals with their left edge past their right edge.
    What makes this worth recording is which fonts can catch it. A font whose
    glyphs are all simple outlines stores no bounding boxes at all, reads
    nothing after the bitmap, and decodes perfectly either way: four of the
    seven test fonts were in that group and said nothing. Only a font with
    composite glyphs - an accented Latin font, or CJK - fails. Testing against
    one real font would not have been enough.

  * The 255UInt16 escape codes are the way round that looks wrong. Code 255
    adds 253 and code 254 adds twice that. Swapping them was tried, on the
    theory that the pair had been transcribed backwards, and three more test
    fonts failed immediately - so the original was right, and the comment in
    Woff2Reader now says so and says how it is known. The codes only appear on
    glyphs with 253 points or more, which is why most fonts decode either way
    and a CJK font and an icon font are what settle it.

  * Preparing a large font folder used 772 MB and kept 732 MB of it. The
    budget in Section 2.1 is 150 MB, so this was the real work of the phase,
    and it took three separate fixes. First, FontInspector was reading fonts
    through the table-copying reader: for a reader that wants four of a font's
    twenty tables, that is the whole font copied to look at a fifth of it, so
    inspecting 396 MB of fonts allocated another 396 MB. A zero-copy directory
    reader - tags and offsets, with the tables read in place - took the peak
    from 772 MB to 353 MB. Second, the file reads were going through
    ArrayPool<byte>.Shared, which keeps its buffers on purpose and cannot hold
    anything over 1 MB: 70 MB of live buffers were still held after the pass.
    A pool scoped to the pass, dropped when it ends, took the live managed heap
    from 70 MB to 6 MB. Third, that pool's buckets are powers of two, so
    allowing it up to the 50 MB file cap let it hold one buffer of 1, 2, 4, 8,
    16, 32 and 64 MB at once - about 127 MB for reading one file at a time.
    Capping pooling at 4 MB and giving the handful of larger fonts a plain
    array each brought the peak to 247 MB and the settled figure to 162 MB.
    What is left is 6 MB of live managed memory and the runtime's own committed
    space, so there is nothing still being held.

One bug worth its own note, because the test suite could not have caught it:

  * A UI callback with no inline fallback. FontRegistry marshals its progress
    and change notifications onto the UI thread, and when there was no
    Application it ran them inline instead. That is exactly the state during
    --measure-startup, which shuts down at the first frame: the callback then
    touched the status bar from the preparation thread, threw "the calling
    thread cannot access this object", and took the whole folder check down
    with it - so the index was never saved and every measurement run prepared
    the entire font folder again from scratch. It was visible only as four
    ERROR lines in the log and a startup figure that would not settle. There
    is no sensible inline fallback for a UI update: if there is no UI, there is
    nothing to tell. --measure-startup now also skips font preparation
    outright, because a measurement run doing work a real launch would not is
    not a measurement.

Two deliberate deviations from the blueprint:

  * Section 6.6.2 step 6 says to read the family names by loading the font once
    with WPF's Fonts.GetFontFamilies. FontInspector reads them out of the name
    table instead. Two reasons: WPF keeps a font file open once it has read it,
    which is the thing the cache copy exists to avoid, and reading names
    through WPF would put a WPF dependency in Core, where the compiler is set
    up to refuse one. The App tests load every decoded font through WPF and
    check its families and glyph count, so the guarantee that mattered - that
    DirectWrite can actually read what was produced - is still tested, just
    not during preparation.

  * SfntBuilder was listed in Section 5.1 under Fonts/Type1/, described as
    "shared by every decoder and converter". The WOFF decoders need it in
    Phase 2 and Type 1 is Phase 3, so the shared container code is
    Fonts/Sfnt.cs and the stub under Type1/ is gone rather than left throwing.
    A shared helper filed under one caller's folder is misleading about who
    uses it. Phase 3 still needs the other half of what that name covered -
    synthesising head, hhea, maxp, hmtx, post, OS/2, name and cmap for a
    converted Type 1 font - and that belongs with the Type 1 code.

Not built in this phase
-----------------------

  * WOFF2 font collections. Section 6.6.5 asks for them. A collection needs a
    second directory, shared glyf and loca tables across fonts, and a third
    index layer, and web fonts are effectively never collections - no .woff2
    collection was found to test against. A collection is refused with a
    message naming the .ttc or the individual .otf files instead, which is
    checked by a test. Say the word if it should be built anyway.

  * Adobe Type 1 (.pfb, .pfa), Mac containers (.dfont, ._*), EOT and Type 42.
    These are Phase 3 as planned. They are detected and named now, so the Font
    Report says each one cannot be used yet rather than ignoring the file.

  * The missing-font bar is built and tested but has no caller: it lists the
    fonts a document asked for, and nothing can open a document until Phase 4.

Why
---

Everything after this phase edits a document, so the document had to come
first, and the two decisions worth recording are about what formatting means
rather than how it is stored.

Clear Formatting returns a paragraph to its style rather than to nothing. A
heading with Clear Formatting applied should still be a heading; it is the
by-hand changes on top that go. That is what Word does and what Section 6.5
describes, and it is why ClearAllProperties alone is not the whole command -
the paragraph's style is re-applied afterwards.

Change Case rewrites the letters instead of setting a format. WPF has no
all-caps character format, so there is nothing to save to a .docx; changing the
letters themselves means the result survives every format in Section 7, which
is the point.

The paste filter downgrades XAML to RTF to plain text. WPF offers pasted
content as XAML, and XAML is not markup here - it is a serialized object graph
that the control would instantiate. Pasting from a web page should not be able
to construct objects, so that flavour is dropped before it is read.

Themes arrived two phases early. Section 6.16 puts them in Phase 8, but the
toolbar button styles need themed brushes to render at all, and a toolbar
styled against hard-coded colors now would have to be unpicked later. The
dictionaries, ThemeManager and the dark title bar are therefore in, which is a
deviation from the phase plan in the direction of less rework.

How
---

Five things about WPF turned out differently from the blueprint or from the
obvious implementation. Each one is recorded where it bites, in the code as
well as here.

  * TextRange cannot carry the attached properties. Sections 6.4 and 6.8 say
    to store the underline kind, the super/subscript alignment and the base
    font size through the selection, but TextRange.ApplyPropertyValue and
    GetPropertyValue accept only WPF's own text-formatting properties and throw
    ArgumentException - "'Underline' property is not valid for text
    formatting" - for anything else. This is not a detail; it is the mechanism
    two sections of the blueprint are built on, and it broke 14 tests.
    What replaces it: SpProps.ApplyToSelection and ReadFromSelection walk the
    inline elements the selection covers and set or read the value on each one,
    and all five properties are registered with
    FrameworkPropertyMetadataOptions.Inherits so a value set on a span is still
    readable from the runs inside it. Call order matters and is commented at
    every call site - the real WPF property goes on first, because applying it
    is what makes WPF split runs at the selection edges, and the attached
    property then lands on the runs that now exist.

  * Commands have to be public, and the test suite had to be able to say so.
    The menus reach the commands with {x:Static}, which XAML resolves at parse
    time by public reflection. The commands were internal. That compiled
    without a warning, every unit test passed, and the app threw
    ArgumentException the instant MainWindow's XAML was parsed - dead before
    its first frame, on every launch. The real fault was in the tests: each
    one checked a class in isolation and nothing ever loaded the window.
    MainWindowTests now builds the real MainWindow, shows it, lays it out and
    reads the commands back off the menu items, and AppHost gives those tests
    one STA thread with a real Application so the toolbars find their
    StaticResource styles. The rule from here: anything the app parses or
    renders at startup is loaded by a test, not just the classes behind it.

  * Application.ThemeMode is still experimental in .NET 10. It exists, but
    using it raises WPF0001, and this project builds with warnings as errors,
    so taking it would mean suppressing a diagnostic that says the API may
    change. The hand-written Light and Dark dictionaries stay, and a test
    asserts the two have identical key sets - a key present in one and missing
    from the other shows up as an unpainted control, which is easy to ship and
    hard to spot.
    Writing that test found a second thing: ThemeManager loaded its dictionary
    from the relative URI "UI/Themes/Light.xaml", and a relative pack URI
    resolves against the entry assembly. That is this one when the .exe starts
    the process, and the test runner otherwise, so the theme failed to load
    with "Cannot locate resource" under test. It now builds the full
    pack://application URI with this assembly named, taking the name from the
    assembly rather than a string, and both the app and the tests go through
    the same method.

  * Undo needs a hosted control. CanUndo is false for every edit on a
    RichTextBox that is not in a visual tree, a plain text change included, so
    the first version of the undo tests was asserting something that could not
    be true. They now show a window with ShowActivated false, which gives a
    live undo stack, and the test that earns BeginChange/EndChange its place is
    the double underline: it writes two text decorations and an attached
    property, and one Ctrl+Z has to take back all of it.

  * The two drawn underlines and the paper shadow are hand-made. WPF offers
    one underline, so double is two pens at different offsets, dotted and
    dashed are dash patterns, and wavy is a tiled DrawingBrush of bezier
    curves; all of them are frozen, since they never change. The paper shadow
    is two offset borders rather than a DropShadowEffect, because an Effect
    allocates a render target the size of the whole document.

Two smaller notes:

  * Superscript applied over subscript would have shrunk the text twice, to
    4.2pt from 10pt, which is why the base size is kept in an attached property
    and the size is computed from it rather than from the current size. There
    is a test named for that case.
  * The selection readout runs at DispatcherPriority.Background behind a 50 ms
    throttle, and the word count behind a 300 ms timer. Both run on every
    keystroke otherwise, and typing is the one thing in this app that must
    never feel slow.

Not built in this phase
-----------------------

  * Show Formatting Marks. WPF cannot draw paragraph marks and space dots
    inside a RichTextBox without a custom adorner. The menu item is present and
    disabled with a tooltip saying so, rather than half-built or quietly
    missing.
  * The font picker lists the fonts Windows has. The fonts/ folder, the
    converted formats and the Font Report are Phase 2 and 3, as planned.

Watch
-----

Idle working set went from 124.1 MB in Phase 0 to 143.6 MB here, against the
150 MB in Section 2.1. Private bytes are 81.6 MB and comfortable; the growth is
in the mapped pages that come with parsing this much more XAML. Phase 2 adds
the font index, so on the working-set reading the budget is close to spent. The
question of which figure Section 2.1 means is raised in the Phase 1 report
rather than decided here.

Why
---

Phase 0 exists to make the later phases cheap. Three things in particular had
to be settled before any feature work:

  * Where files live. A portable app that guesses wrong about its data folder
    is broken on a USB stick and broken in Program Files, and that is hard to
    retrofit, so AppPaths and the read-only fallback come first.
  * The startup budget. Section 2.1 is the top-priority rule in the blueprint,
    and a budget nobody can measure is not a budget. The timer, the hidden
    measurement flag and the median in build.ps1 exist so every later phase can
    be checked against the number rather than against an impression.
  * The shape of the tree. Every file in Section 5.1 is present as a documented
    stub, so a phase starts by filling in a file that already knows what it is
    for, and nothing has to be reorganised halfway through.

The full menu structure is in the window for the same reason: the shortcut table
in Section 8.3 only works if every shortcut is defined in one place, and that is
much easier to keep true from the start than to impose later.

How
---

  * ScratchpadLite.Core targets plain net10.0, with no WPF reference. That is
    not a convention to remember; the compiler refuses the alternative, which is
    what keeps the format and font code testable without a window.
  * Everything that costs time at startup is deliberately on the far side of
    ContentRendered: fonts, recovery, spell check, the format libraries and the
    timers all start after the first frame, and App.OnStartup carries a comment
    saying so, because that is where the budget gets lost.
  * The format registry keeps names and extensions in a static table and creates
    each handler through Lazy<T>, so building an Open dialog filter loads no
    format package and .NET never pulls in the Open XML SDK at startup.
  * --measure-startup needed one thing the blueprint did not mention: this is a
    WinExe, so it has no console and a plain Console.WriteLine goes nowhere.
    It attaches to the console of the process that launched it, which is what
    lets build.ps1 read the number; a double click fails the attach harmlessly
    and the value is still in the log.
  * One deviation from Section 11.1, noted in the .csproj: SupportedOSPlatform-
    Version 10.0.17763.0 is rejected on a bare net10.0-windows TFM, whose
    TargetPlatformVersion is 7.0. Raising it means a net10.0-windows10.0.x TFM,
    which pulls in the Windows SDK WinRT projections. Nothing here uses WinRT -
    spell check comes through WPF and the dark title bar through a DWM P/Invoke -
    and Section 2.1 says a dependency has to earn its place, so the TFM stays
    lean and the Windows 10 1809 floor is declared in app.manifest and the
    README instead.
  * A placeholder app.ico is generated into Resources; it is a plain mark and
    is meant to be replaced.
  * Two dialog classes are named ParagraphDialog and PageSetupDialog rather than
    Paragraph and PageSetup, because those two names are already taken by WPF
    and by the IR respectively, and a type that shadows either one is a trap.

It is the fastest and it is also the one that keeps the app a single file, so
there was nothing to weigh up and nothing to ask about. Variant 2 saves 8 MB,
is 35 ms slower, and scatters native DLLs beside the .exe; it loses on both
counts.

Turning compression on is the real trade: it cuts the .exe from 141 MB to
63 MB, and costs 222 ms, which is 42% of the startup budget for a file size
nobody sees after the first unzip. Section 2.1 says speed wins when speed and
size conflict, and this is what that rule was written for.

The shipped zip is 58.5 MB either way, because Compress-Archive compresses the
uncompressed .exe about as well as the single-file packer would have. That is
the whole argument against variant 3 in one line: the download is the same size
and the app opens slower.
